Where your tasks live on the network

VPC, subnets, security groups and the load balancer, for a forecast API and a nightly planner

Your win for this lesson (about 25 minutes) You can sketch the standard network layout for a Fargate app: a load balancer in public subnets and tasks in private subnets, with NAT or VPC endpoints for outbound traffic and chained security groups. When something can't connect, you'll know which piece to check.

Every network design question comes down to two things: what may come in and how does it get out. Both apps need a way out, because a task can't even start without pulling its image. Only the API needs a way in.

Way in: the load balancer path

AWS's guidance for a container serving internet traffic from a private subnet: put a load balancer in a public subnet and let ECS forward traffic to tasks in the private subnet.[1] Four details make it work:

  • The ALB spans at least two AZs. You must give it subnets in at least two different Availability Zones.[2] Run your tasks in matching private subnets in both AZs too.
  • The target group uses type ip. With awsvpc, "you must choose ip as the target type, not instance", because each task is its own network interface, not an EC2 instance.[3]
  • ECS keeps the target list up to date for you. "When each task starts, the IP address of its elastic network interface is added to the load balancer's configuration," and traffic is drained before a task is removed.[1] When autoscaling goes from 2 to 4 tasks, the new IPs simply appear in the target group.
  • Health checks hit your /health. The ALB sends traffic only to targets that pass. The service's health check grace period tells ECS to ignore failing checks for a while after a task starts.[4] That gives your model time to load.

Way out: NAT gateway or VPC endpoints

Here's the part that catches most people: "For a task on Fargate to pull a container image, the task must have a route to the internet." The docs list three ways to give it one:[5]

OptionHowGood for
Public subnet + public IPassignPublicIp: ENABLEDQuick experiments only, because the task is directly on the internet
NAT gatewayPrivate subnet route → NAT in a public subnetTasks that also call non-AWS internet services (a third-party API, pip install at runtime)
VPC endpointsPrivate tunnels to specific AWS servicesTraffic that never needs the public internet. A Fargate task pulling from ECR needs ecr.dkr, ecr.api and the S3 gateway endpoint, plus logs for awslogs and secretsmanager if you use secrets[6]

Why does ECR need the S3 endpoint? An image pull first asks ECR for the image manifest, then downloads the actual image layers from S3.[10] Your planner reads and writes S3 as well, so it uses that same endpoint. If none of these paths exist, the classic symptom is a task stuck in PENDING, then failing with an image-pull or ResourceInitializationError.[7]

Both NAT gateways and interface endpoints charge per hour plus per GB of traffic, so it's a design choice, not a free default. We'll leave cost to a later lesson.

Security groups: guest lists that reference each other

Don't write a task's guest list as "allow port 8000 from anywhere in the VPC". Write it as "allow 8000 from whoever carries the ALB's security group". Recommended rules allow traffic from the load balancer's security group rather than from IP ranges.[8]

Security groupInbound ruleMeaning
sg-albTCP 443 from 0.0.0.0/0Anyone on the internet may talk to reception
sg-forecast-tasksTCP 8000 from sg-albOnly reception may talk to API tasks
sg-plannernoneNobody may start a connection to the planner. It can still reach out

The planner with zero inbound rules is not a mistake. Security groups track connections, so the replies to the planner's own outbound calls (to S3, ECR and so on) are let back in automatically. "No inbound rules" just means nobody can start a conversation with it.

Where it all goes in config

Here's the forecast API's service definition: the WHERE from lesson 2, plus the load balancer. As before, say out loud what each highlighted part does, then click to check.

{
  "serviceName": "forecast-api",
  "cluster": "prod",
  "taskDefinition": "forecast-api:12",
  "desiredCount": 2,
  "launchType": "FARGATE",
  "networkConfiguration": {
    "awsvpcConfiguration": {
      "subnets": ["subnet-private-a", "subnet-private-b"],
      "securityGroups": ["sg-forecast-tasks"],
      "assignPublicIp": "DISABLED"
    }
  },
  "loadBalancers": [{
    "targetGroupArn": "arn:aws:elasticloadbalancing:us-east-1:111122223333:targetgroup/forecast-api-tg/…",
    "containerName": "api",
    "containerPort": 8000
  }],
  "healthCheckGracePeriodSeconds": 120
}
networkConfiguration.awsvpcConfiguration: the WHERE for an awsvpc task. It's required for awsvpc tasks and isn't supported in other modes.[9] RunTask takes exactly the same block, which is how the planner gets its subnets.
subnets: private subnets in two AZs, all in the same VPC. ECS spreads tasks across them, so losing one AZ doesn't take the API down.
securityGroups: the guard on each task's network interface. Its only inbound rule is 8000 from sg-alb.
assignPublicIp: DISABLED: the tasks aren't reachable from the internet. They reach out through NAT or VPC endpoints instead.
loadBalancers.targetGroupArn: the ALB target group (type ip) where ECS registers each task's IP as it starts and removes it as it stops.
containerName / containerPort: which container in the task receives the traffic, and on which port. It must match a containerPort in the task definition's portMappings.[3] This is why the API, unlike the planner, has port mappings.
healthCheckGracePeriodSeconds: how long ECS ignores failing ALB health checks after a task starts.[4] Set it longer than your model takes to load, or ECS will keep killing tasks that are still starting up.

Practice: find the broken piece

Your questions from this session

Try to answer each one out loud before opening it.

Why port 8000 for the forecast API?

It isn't an AWS rule. 8000 is Uvicorn's default port, and Uvicorn is the server that usually runs FastAPI.[11] Any port works, as long as five places agree:

1. App listens on       uvicorn app:api --host 0.0.0.0 --port 8000
2. Task definition      "portMappings": [{ "containerPort": 8000 }]
3. Service              loadBalancers[].containerPort = 8000
4. Target group         port 8000, health check /health
5. Task SG              inbound TCP 8000 from sg-alb
  • If one of them differs, the ALB knocks on a port where nothing is listening. Health checks fail and tasks get replaced over and over.
  • Customers never see 8000. They use 443 on the ALB, and 8000 is only the internal hop.
  • Bind to 0.0.0.0. Uvicorn defaults to 127.0.0.1,[11] which inside a container means "only reachable from within this task", so the ALB can't reach it.
  • Ports above 1024 avoid needing root inside the container.
