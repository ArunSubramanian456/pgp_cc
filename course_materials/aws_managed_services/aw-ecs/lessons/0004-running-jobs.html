Running one job well

RunTask, the task lifecycle, exit codes, and a 1am schedule for the MILP planner

Your win for this lesson (about 25 minutes) You can start the nightly planner with RunTask, follow it through its lifecycle, tell from its stopCode and exit code whether last night's plan actually succeeded, and put it on a schedule with EventBridge Scheduler. You'll also know why "the schedule fired" does not mean "the plan was written".

Warm-up

1 · Anatomy of a RunTask call

RunTask "starts a new task using the specified task definition".[1] Here is tonight's planner run in boto3. You've already met the network block and overrides. Say out loud what each highlighted part does, then click to check.

import boto3
ecs = boto3.client("ecs")

resp = ecs.run_task(
    cluster="planning",
    taskDefinition="replenishment-planner:3",
    count=1,
    capacityProviderStrategy=[{"capacityProvider": "FARGATE", "weight": 1}],
    networkConfiguration={"awsvpcConfiguration": {
        "subnets": ["subnet-private-a", "subnet-private-b"],
        "securityGroups": ["sg-planner"],
        "assignPublicIp": "DISABLED"}},
    overrides={"containerOverrides": [{
        "name": "solver",
        "environment": [{"name": "PLAN_DATE", "value": "2026-10-22"}]}]},
    startedBy="nightly-2026-10-22",
    clientToken="replenishment-2026-10-22",
)
if resp["failures"]:
    raise RuntimeError(resp["failures"])
task_arn = resp["tasks"][0]["taskArn"]
taskDefinition: pin the exact revision (:3). If you leave it out, ECS uses the latest revision,[1] so whoever registers a new revision during the day would silently change tonight's solve.
count: how many identical copies to start, up to 10 per call.[1] The planner needs one. Lesson 5 deals with running 200.
capacityProviderStrategy: which kind of Fargate to use. FARGATE is on-demand. For Spot you must use FARGATE_SPOT here, because the launchType parameter has no Spot option. Use either launchType or a capacity provider strategy, never both.[1] The nightly plan is business-critical, so it stays on on-demand.
networkConfiguration: the WHERE from lesson 3. Private subnets in two AZs, a security group with no inbound rules, and no public IP.
overrides: per-run inputs (lesson 2). Here it's the plan date. The 8,192-character limit still applies.
startedBy: a tag (up to 128 characters) so you can list exactly which tasks belong to tonight's run.[1]
clientToken: protection against starting the job twice. If you retry with the same token and the same parameters, ECS returns the original task instead of starting a new one. The token stays valid for up to 24 hours.[2] If your script times out and retries, you still get one planner, not two writing the same plan.
failures: RunTask can return a successful response that still lists tasks it couldn't start (in failures), for example for capacity reasons. Always check it.

3 · Did last night's plan actually succeed?

A STOPPED task carries two clues. One is the task's stopCode: why ECS considers it stopped, such as TaskFailedToStart, EssentialContainerExited or UserInitiated.[4] The other is each container's exit code, which is how your process ended:[5]

Exit codeMeaningFor the planner
0The command completedPlan written, as long as your code only exits 0 after the S3 write succeeds
1Application errorA Python exception, an infeasible model your code treats as an error, bad input. Check the logs
137Killed with SIGKILL: it ignored SIGTERM past the timeout, or ran out of memoryA branch-and-bound tree that outgrew 32 GB. Check the memory metrics
143Stopped by SIGTERM, the graceful-shutdown signalSomeone or something stopped it, e.g. a deployment or a Spot interruption
Your exit code is a contract ECS and every tool built on it judge your job only by these codes. If your solver catches an infeasibility, logs "no feasible plan" and then exits 0, everything downstream thinks the night went fine. Decide on purpose what counts as failure, and exit non-zero for it.

The details of a stopped task only stay visible through DescribeTasks for about 1 hour.[5] You won't be awake at 1:45am, so capture them as they happen. ECS publishes task state change events to EventBridge, with lastStatus, stopCode and stoppedReason included.[6] An EventBridge rule can match "planner task reached STOPPED" and send it to SNS, the service you covered in your course's messaging module, which emails you when the exit code isn't 0.

4 · Putting it on a 1am schedule

EventBridge Scheduler calls an API for you on a schedule, with no cron server to run. It has a templated target for ECS RunTask, and you can pass container overrides through it.[7]

Schedule  "nightly-replenishment"
  ScheduleExpression          cron(0 1 * * ? *)        ← minute hour day-of-month month day-of-week year
  ScheduleExpressionTimezone  America/New_York          ← your business's time zone, not UTC
  FlexibleTimeWindow          OFF                       ← run at 01:00, not "sometime around"
  Target
    Arn        arn:aws:ecs:…:cluster/planning
    RoleArn    scheduler-run-planner                    ← a THIRD role (see below)
    EcsParameters
      TaskDefinitionArn  …:task-definition/replenishment-planner:3
      LaunchType         FARGATE
      NetworkConfiguration  (private subnets, sg-planner, no public IP)
    RetryPolicy       MaximumRetryAttempts 2
    DeadLetterConfig  sqs: scheduler-dlq
  • Cron has six fields, including year.[8] cron(0 1 * * ? *) means "minute 0 of hour 1, every day". The ? means "no specific value", because you set day-of-month or day-of-week, not both.
  • Time zone. Scheduler can run cron in UTC or in a time zone you choose,[8] so "1am" stays 1am local time when the clocks change.
  • A third role. The Scheduler has its own execution role, which it assumes to call RunTask for you.[9] It also needs permission to pass your task's roles to ECS (iam:PassRole). The console can create it for you.
  • Retries and the dead-letter queue (DLQ) cover a failure to deliver the invocation. After the retries are used up, the failed event goes to an SQS DLQ.[10]
"The schedule fired" ≠ "the plan was written" The Scheduler's job ends once it has called RunTask. Its retries and DLQ are about that call. If the solver then crashes with exit code 1 at 1:37am, the Scheduler doesn't know and won't retry. Watching the result is section 3's job: task state change events, then SNS.
