Choosing compute and cost

Same task definitions, different engines underneath: which one each of your apps should run on, and roughly what it costs

Your win for this lesson (about 25 minutes) For any of your apps, you can choose between Fargate, Fargate Spot, Managed Instances and the EC2 launch type, say whether Express Mode or ARM fits, justify the choice, and estimate the monthly Fargate bill on paper.

Warm-up

From lessons 1, 5 and 9. Answer from memory before you click.

1 · The options, side by side

Everything you've learned (task definitions, services, RunTask, scaling) stays the same. What changes is where the tasks physically run. That's chosen by the capacity provider, which you met in lesson 4 as capacityProviderStrategy.

Who runs the serversYou pay forCan't do / watch out
FargateAWS. You never see a server. Each task gets its own isolated environment.The vCPU and memory each task asks for, per second (1-minute minimum), from the start of the image pull until the task stops[1]No GPUs. At most 32 vCPU and 244 GB per task, in fixed size combinations. No privileged containers.[2]
Fargate SpotAWS, on spare capacityUp to 70% less than Fargate[1]Can be taken back with 2 minutes' warning. Linux only (x86 or ARM).
Managed InstancesAWS launches, patches and replaces real EC2 instances in your account; you pick the instance typesThe EC2 instance price plus a management fee per instance. Reserved Instances, Savings Plans and Spot apply to the EC2 part.[3]Several tasks can share one instance, so less isolation than Fargate. You pay for the instance even when it's half empty.
EC2 launch typeYou: an Auto Scaling group of instances, their AMIs, patching and scalingThe EC2 instancesThe most work. Worth it only for control the others don't give (custom AMIs, special host setup).

When do you need more than Fargate? AWS's own list for Managed Instances: GPUs, more than 32 vCPU or 244 GB, privileged containers or host devices, specific instance types, or using reservations and Savings Plans you already have.[4] If none of those apply, AWS's advice is simple: Fargate.

GPUs no longer mean "manage EC2 yourself" A deep-learning forecaster that needs an NVIDIA GPU can't run on Fargate (lesson 1). Managed Instances can run it on GPU instances without you running servers, and can scale to zero instances between batch jobs, so you pay only while a job runs.[5] The EC2 launch type is now the choice only when you need full control of the host.

2 · Two settings that cut the bill

Both live in ECS JSON you already know how to read.

// in the task definition
"runtimePlatform": { "operatingSystemFamily": "LINUX", "cpuArchitecture": "ARM64" }

// on the service (or in RunTask)
"capacityProviderStrategy": [
  { "capacityProvider": "FARGATE",      "base": 2, "weight": 1 },
  { "capacityProvider": "FARGATE_SPOT", "weight": 3 }
]
ARM64 (AWS Graviton): on Fargate, ARM costs about 20% less per vCPU and per GB than x86 (us-east-1: $0.0324 vs $0.0405 per vCPU-hour).[1] The catch: the image must be built for arm64 (or as a multi-architecture image), and every native library inside it needs an ARM build. Pure Python with mainstream wheels (numpy, pandas, scikit-learn) is usually fine. Check commercial solvers and less common compiled packages before you switch.[6]
base: the first 2 tasks always go on regular Fargate. For the Scenario Lab workers, that means some progress is guaranteed even if Spot capacity disappears.
weight: beyond the base, tasks are split 1 : 3 between Fargate and Fargate Spot. With 10 tasks: 2 base, then 8 split as 2 Fargate and 6 Spot. Mostly cheap, never all at risk.

The third lever is commitment: Compute Savings Plans cut Fargate prices by up to 50% in return for committing to a fixed amount of spend per hour for one or three years.[1] That's only worth it once your usage is steady and predictable.

3 · Express Mode: a shortcut, not a different engine

Express Mode isn't another place to run tasks. It's a quick way to build a web service on Fargate. You give it three things: an image, a task execution role and an infrastructure role (which lets ECS create resources for you). It then creates everything from lessons 3, 6, 7 and 9:[7]

  • a task definition with logging and networking, and a service using canary deployments
  • an Application Load Balancer with HTTPS (and an ACM certificate), security groups and a target group
  • auto scaling with a target tracking policy, a log group, and alarms that catch a bad deployment

These are ordinary resources in your account, so you can change them later: add a task role, a sidecar, scaling policies, a custom domain.[8] Up to 25 Express services in the same subnets can share one load balancer.[9]

Fits: the forecast API or the agent assistant, which are HTTP services that receive traffic. Doesn't fit: the nightly planner, the solve worker and Scenario Lab, which receive no web traffic. Build those the way you learned in lessons 4, 5 and 7.

Having done lessons 1 to 9, you'll understand every resource Express Mode creates. That's what it's for: going fast without it being a black box.

4 · Rough cost on paper

Fargate's price has two parts: vCPU-hours and GB-hours. us-east-1 Linux prices, rounded (checked October 2026; always check the pricing page for your Region):[1]

             per vCPU-hour   per GB-hour
x86          $0.0405         $0.0044
ARM64        $0.0324         $0.0036

monthly cost ≈ tasks × hours × (vCPU × vCPU price + GB × GB price)
always-on    = 24 × 30 = 720 hours a month

The Fargate line isn't the whole bill. Load balancers, NAT gateways, public IPv4 addresses, CloudWatch Logs and data transfer are charged separately.[1] For a small app, the ALB and NAT gateway can cost more than the tasks. That's one reason VPC endpoints (lesson 3) and shared Express Mode load balancers matter.

5 · Choosing, in order

1. Needs a GPU, more than 32 vCPU / 244 GB, privileged mode or a specific instance type?
     yes → Managed Instances  (EC2 launch type only if you need full control of the host)
     no  → Fargate
2. Safe to interrupt and retry?            yes → Fargate Spot, often with a Fargate base
3. All native libraries have ARM builds?   yes → ARM64, about 20% off
4. A web service that receives traffic?    yes → consider Express Mode to set it up
5. Steady usage for a year or more?        yes → Compute Savings Plan

Practice: choose the compute

Your questions from this session

Try to answer each one out loud before opening it.

How does ARM vs x86 affect my Docker image? If it works on my AL2 or Ubuntu dev box, won't it work on ECS with the same distro?

The distro doesn't need to match. The CPU architecture does.

  • Distro: carried by the image. A container brings its own userland from its base image (python:3.12-slim is Debian, whatever the host runs). It shares only the host's Linux kernel. That's why an Ubuntu laptop can run an Alpine container, and why Fargate doesn't let you choose a distro at all, just LINUX plus a CPU architecture.
  • Architecture: baked into the image. Every compiled binary inside it (the Python interpreter, numpy's C code, a solver library) is machine code for one CPU family. docker build builds for the machine it runs on, so an x86 dev box produces an amd64 image, and an Apple Silicon Mac or a Graviton instance produces arm64.

Your .py files run anywhere, but pip install downloads compiled wheels for the build machine's architecture, so the finished image is single-architecture.

What a mismatch looks like: an amd64 image in a task with "cpuArchitecture": "ARM64" pulls fine, then fails as soon as it starts: the logs show exec format error, and the task stops with "Essential container in task exited", exit code 1.[10] If you leave out runtimePlatform, Fargate uses x86, so an x86-built image just works.

Three ways to get an ARM image:

# 1. Build on an ARM machine (Graviton instance, Apple Silicon Mac): plain docker build

# 2. Cross-build from x86 with buildx (emulated: slow for heavy ML builds)
docker buildx build --platform linux/arm64 -t REPO:TAG --push .

# 3. One multi-architecture image for both
docker buildx build --platform linux/amd64,linux/arm64 -t REPO:TAG --push .

# check what you've got
docker buildx imagetools inspect REPO:TAG

Option 3 pushes an image index under one tag, pointing at one image per architecture. Each task pulls the one that matches its cpuArchitecture, so the same tag works on x86 and ARM. The base image must exist for both (official python images do), and so must every wheel you install.

Rule of thumb: the test that counts is running the arm64 image, not the x86 one. Run your test suite inside it once before switching a service to ARM64.
