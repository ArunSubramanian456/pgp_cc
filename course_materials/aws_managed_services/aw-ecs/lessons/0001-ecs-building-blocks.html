Mission · Lesson 1 · Cheat sheet

The four building blocks of ECS

and what Fargate quietly takes off your plate

Your win for this lesson (about 15 minutes) Given any situation with your app ("it crashed", "I changed the image", "run this script once"), you can say which ECS object is involved: cluster, task definition, task or service. And you can say which jobs are yours and which are AWS's when you run on Fargate.

Start from what you already know

You've built Docker images and run them with docker run. ECS doesn't replace any of that. Your image stays the same. ECS answers the questions that come after the image exists: where does it run, how many copies, with how much CPU, and who restarts it when it dies at 2am?

Here's a rough translation from Docker words to ECS words. It's an analogy, not an exact match, but it's a good place to start:

On your laptopIn ECS
The flags you give docker run: image, ports, env vars, --memoryTask definition: a saved JSON blueprint of those settings
A container you started with docker runTask: one running copy of the blueprint (it can hold one or more containers)
"Keep 3 of these running and restart any that die"Service: keeps your chosen number of tasks running
Your machineCluster: a logical group your tasks and services live in. On Fargate there's no machine for you to see.

The four objects, as AWS defines them

1 · Task definition: the blueprint

"A blueprint for your application. It is a text file in JSON format that describes the parameters and one or more containers that form your application."[1] It holds the image, CPU and memory, ports, logging, the IAM role and more. Every time you change it you get a new numbered revision (my-api:1, my-api:2…). That's how ECS keeps a history of your settings.[2]

2 · Task: one running copy

"A task is the instantiation of a task definition within a cluster."[1] It's "made of a group of one or more containers that run together", which start and stop together and share localhost.[3] If you run a task by itself (a standalone task), it runs until it finishes and nobody restarts it. That's what you want for a one-off job like a database migration.

3 · Service: the thing that keeps tasks alive

A service "runs and maintains your desired number of tasks". If a task "fail[s] or stop[s] for any reason, the Amazon ECS service scheduler launches another instance based on your task definition."[1] Your web API will almost always run as a service. Services are also what connect to a load balancer and get rolled to new revisions during a deploy.

4 · Cluster: the grouping

"A logical grouping of services or standalone tasks."[3] On Fargate, a cluster is mostly a name and a boundary, for example staging vs prod. It isn't a set of servers you look after.

So what does Fargate change?

Every task has to run on some compute. ECS gives you three options: Fargate (serverless), Auto Scaling group EC2 capacity (you manage the instances), and ECS Managed Instances (AWS manages EC2 instances for you).[6] With Fargate, "you no longer have to provision, configure, or scale clusters of virtual machines to run containers. This removes the need to choose server types, decide when to scale your clusters, or optimize cluster packing."[4]

Three facts about Fargate you'll keep running into:

  • Each task is isolated. "Each Fargate task has its own isolation boundary and does not share the underlying kernel, CPU resources, memory resources, or elastic network interface with another task."[4] Each task gets its own Fargate resource, so tasks and compute are 1:1.[7]
  • Each task gets its own network card. Fargate always uses the awsvpc network mode, so every task gets its own elastic network interface, and with it a private IP address in your VPC.[5] (This matters later for load balancers.)
  • You size the task. You set CPU and memory at the task level, and they must be one of the valid combinations Fargate supports (for example 256 CPU units with 512 MiB).[5] You don't pick a machine.
The one-sentence version You describe the app (task definition) and how many copies to keep (service). AWS finds the compute, isolates each task, and patches what's underneath.

Your questions from this session

These are the follow-ups you asked, kept short. Try to answer each one out loud before opening it.

"A task has one or more containers." So is that frontend + backend + database in one task?

No. A task is one copy of one part of your app. The extra containers in a task are sidecars, small helpers like a log router, telemetry agent or proxy that enhance that one container. AWS: "Don't use this feature to add multiple application containers to the same task definition because this prevents copies of each application scaling separately."[8]

✓ Task (forecast-api)          ✗ Task
  ├── api                        ├── frontend
  └── otel-collector (sidecar)   ├── backend
                                 └── postgres

Bundling breaks things because containers in a task start, stop and scale together. Five tasks would mean five frontends, five backends and five separate databases. Instead, give each part its own task definition + service. The database usually lives outside ECS (e.g. RDS), because Fargate task storage is temporary.[5]

Rule of thumb: put two containers in one task only if they always run 1:1 and it's fine for them to restart together.

If a task can hold several containers, why would I ever need multiple tasks?

Multiple tasks are identical copies of the same thing. You run them for load (three copies behind a load balancer handle about three times the traffic) and for resilience (if one copy or one Availability Zone fails, the others keep serving while the service replaces it).

What does the :3 in frontend:3 mean?

It's family:revision, so revision 3 of the task definition family frontend. Revisions start at 1 and "always increase by one", even if you deregister old ones.[9] You never edit a revision. Any change registers a new one. A service points at one exact revision, so rolling back means pointing it back at the previous one.

These are independent. Changing only an env var creates a new revision but needs no image rebuild.

Can I say "always at least 2 copies, up to 4 at peak"? (preview of a later lesson)

Yes. That's Service Auto Scaling with a minimum of 2 and a maximum of 4. "The desired count doesn't go below the minimum or above the maximum."[10] You don't say "it's peak now". You set a target-tracking policy (e.g. average CPU 60%, or requests per task), and ECS adds and removes tasks to stay near it. It scales out fast and scales in gradually.[11]

Notes for ML inference:

  • No GPUs on Fargate.[5]
  • Loading the model makes startup slow, so keep a minimum of 2 and use a health-check grace period.
  • Your /health endpoint is what the load balancer checks before it sends a task traffic.
How do my own apps (forecasting, MILP, agents) map onto ECS?

By the shape of the work:

  • Request/response (forecast API, quick what-if LP) → service behind a load balancer.
  • Run, finish, exit (nightly MILP planner, weekly retraining) → standalone or scheduled task.
  • Bursty, slow, many (Scenario Lab: 200 what-if MILPs or forecasts, compared against a baseline) → queue + worker service, all running the same task definition with different inputs.

Choosing the right shape is half of designing an app on ECS. Later lessons cover each one.
