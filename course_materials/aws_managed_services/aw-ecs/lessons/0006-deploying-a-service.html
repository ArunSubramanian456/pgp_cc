Deploying a service safely

Shipping a new forecast model to a live API with no downtime, and an automatic way back

Your win for this lesson (about 25 minutes) You can predict exactly what ECS does when you ship forecast-api:8 to replace :7: how many tasks run at each moment, when traffic moves, and what happens if the new version is broken. You'll also know which settings make it roll back on its own, and which kind of broken they can't catch.

Warm-up

From lessons 1 to 4. Answer from memory before you click.

1 · What a deployment is

The forecast API is a service running 4 tasks of forecast-api:7 behind an ALB. You've trained a better model, built a new image and registered revision :8. Shipping it is one call:

aws ecs update-service --cluster forecasting --service forecast-api --task-definition forecast-api:8

That call starts a deployment: ECS replaces the service's existing tasks with tasks from the new revision.[1] For a while, old and new tasks run side by side. Each deployment has a rollout state: it starts as IN_PROGRESS, becomes COMPLETED when the service reaches a steady state, or FAILED if it can't.[2]

You also trigger a deployment with "force new deployment" and the same revision, for example to pick up a rotated secret, which is only read when a container starts.

2 · Rolling update: the settings, piece by piece

The default way to deploy is the rolling update. These are the service settings that control it. Say what each highlighted part does, then click to check.

{
  "serviceName": "forecast-api",
  "taskDefinition": "forecast-api:8",
  "desiredCount": 4,
  "healthCheckGracePeriodSeconds": 120,
  "deploymentConfiguration": {
    "strategy": "ROLLING",
    "maximumPercent": 200,
    "minimumHealthyPercent": 100,
    "deploymentCircuitBreaker": { "enable": true, "rollback": true },
    "alarms": { "alarmNames": ["forecast-api-5xx-high"], "enable": true, "rollback": true }
  }
}
desiredCount: 4 tasks in normal running. The two percentages below are percentages of this number.
healthCheckGracePeriodSeconds: after a task starts, ECS ignores failed load balancer health checks for this long. The default is 0.[3] The forecast API needs about 90 seconds to load its model. With 0, the ALB marks new tasks unhealthy before they're ready, ECS replaces them, and the new tasks never get the chance to finish starting. Set it a bit longer than your slowest startup, counting the image pull too.[4]
strategy: ROLLING replaces tasks in batches. Section 4 covers the alternatives (BLUE_GREEN, LINEAR, CANARY).[5]
maximumPercent: the most tasks allowed (running or pending) during the deployment, as a percentage of desiredCount. 200% × 4 = up to 8: ECS may start all 4 new tasks before stopping any old ones. The default is 200%.[5]
minimumHealthyPercent: the fewest healthy running tasks allowed during the deployment. 100% × 4 = never fewer than 4 healthy tasks, so capacity never dips. The default is 100%.[5] 100/200 is the usual zero-downtime choice.[6] Lower values exist for EC2 clusters with no spare room. On Fargate there's no cluster to fill up, so you rarely need them.[1]
deploymentCircuitBreaker: notices when the new revision can't become healthy, marks the deployment FAILED and, with rollback: true, goes back to the last deployment that COMPLETED. See section 3.
alarms: the second safety net. If a CloudWatch alarm you name goes off during the deployment (here: "too many HTTP 5xx errors"), ECS rolls back. This catches problems the circuit breaker can't see. See section 3.

What "healthy" means here

A new task counts towards minimumHealthyPercent only when it passes its checks. With a load balancer, that means the target group health check, plus the container health check if you defined one.[5] That's why the /health endpoint from lesson 3 matters so much: it's what decides whether a deployment can move forward.

Stopping the old tasks gently

Old tasks don't just vanish. First they're removed from the target group (the DEACTIVATING state from lesson 4). The ALB stops sending them new requests but lets in-flight ones finish, for up to the target group's deregistration delay (300 seconds by default).[7] Only then do they get SIGTERM, and SIGKILL after stopTimeout (lesson 2). A forecast request takes under a second, so a 30-second delay would be plenty and makes deployments faster.

3 · When the new version is broken

Suppose :8 is bad. What happens depends on how it's bad.

How :8 is brokenWithout safety netsWith them
It never starts: wrong image tag, missing secret, crashes on import (exit 1)ECS keeps launching replacement tasks, and the deployment sits in IN_PROGRESS for a long time. The :7 tasks keep serving, so customers are fine, but you're stuck.Circuit breaker counts the failures, marks the deployment FAILED and rolls back to :7.
It starts but fails /health, e.g. the model file is missingThe same loop: tasks start, fail health checks, get replaced.
It's healthy but wrong: /health passes, but 30% of forecast requests return 500The deployment completes. :7 is gone, and customers get errors.Alarm-based rollback: the 5xx alarm goes off during the deployment, and ECS rolls back.

How the circuit breaker decides. It watches in two stages. First: do new tasks reach RUNNING? Then: do they pass their health checks (load balancer and container)? Each failed task adds to a count. By default the limit is half the desired count, but at least 3 and at most 200.[8] For the forecast API (desired 4): 0.5 × 4 = 2, which is raised to the minimum of 3. So 3 failed tasks fail the deployment. By default, a task that does become healthy resets the count to 0.[2]

Where it rolls back to: the most recent deployment in the COMPLETED state. If there isn't one (say, the very first deployment of a new service is broken), there's nothing to go back to, and the deployment just stops.[2]

Healthy is not the same as correct The circuit breaker only knows about starting and health checks. A model that loads fine but predicts nonsense, or a code change that returns 500 on some inputs, sails straight through. That's what the alarm is for. It's the same idea as lesson 4's "the schedule fired ≠ the plan was written": every check only proves what it actually tests.

Getting told. When a deployment fails, ECS sends a service deployment state change event to EventBridge (SERVICE_DEPLOYMENT_FAILED), and AWS recommends a rule that watches for it.[2] Send it to SNS, exactly like the planner alerts in lesson 4.

4 · Beyond rolling: blue/green, linear, canary

ECS also has deployment strategies built in that move traffic at the load balancer instead of swapping tasks in batches. The new version (green) starts at full size next to the old one (blue), and the ALB shifts requests between them:[9][10]

StrategyHow traffic movesForecasting example
BLUE_GREENAll at once, in one stepA new feature pipeline you've fully tested and want to flip over in one go
LINEAREqual steps (e.g. 25% at a time), with a pause between stepsA routine model refresh you want to watch grow gradually
CANARYA small share first (e.g. 10%), a pause, then the restA brand-new model architecture: let 10% of requests try it before everyone does

All three have a bake time: after all traffic has moved, the old version keeps running for a while, so rolling back is instant (just send traffic back) rather than a fresh deployment.[9] They use CloudWatch alarms to detect failure. The circuit breaker is for rolling updates only.[5] The trade-off: for a while you pay for both versions at full size.

The details of configuring these (target groups for each version, listener rules, lifecycle hooks) are for when you have an account. For now, know that they exist and when you'd pick each one.

Practice

Your questions from this session

Try to answer each one out loud before opening it.

Is registering a new revision separate from updating the service? How can a wrong image tag break a service update?

Yes, they're two separate steps. Registering :8 just saves a new recipe. Nothing runs, and nothing is checked against the registry. The image field is only a string at that point. update-service is what points the service at :8 and starts the deployment.

1. register-task-definition  → forecast-api:8 saved     (image tag NOT checked)
2. update-service :8         → deployment IN_PROGRESS
3. ECS launches an :8 task   → Fargate pulls the image  ← the tag is checked HERE
4. tag missing               → CannotPullContainerError, task stops, never RUNNING
  • Why it hurts the deployment: step 3 happens during the update. Every new task fails at the image pull, so the service keeps launching replacements that fail the same way. That's stage 1 of the circuit breaker: "do new tasks reach RUNNING?"[2]
  • The same goes for the other two in that row: a missing secret also fails before your code runs (the execution role fetches secrets at startup). A crash on import gets as far as your code, then exits 1.
  • Why customers don't notice: with min 100%, the :7 tasks only stop once :8 tasks are healthy. No healthy :8 task ever appears, so :7 keeps serving.

Follow-up: is a missing tag the only cause? No. CannotPullContainerError means "couldn't pull". The tag can exist and the pull still fails if the execution role can't read from ECR, the task's private subnet has no route to ECR (no NAT or VPC endpoints, lesson 3), or the image is in another account the role can't reach.[11] The reverse trap: a reused tag pulls fine but gives you a different image than you expected. That's the immutability topic in the images lesson.

How it typically happens: you register :8 with tag v8 before the image push finished, or with a typo. The stopped task's reason shows CannotPullContainerError.[11] Lesson 8 covers reading these.

What's the difference between the ALB health check and a container health check?

Who asks, and from where. The ALB health check comes from outside: the load balancer sends an HTTP request over the network to the task's IP and port. A container health check runs inside: ECS runs a command in the container and looks at its exit code.

ALB health checkContainer health check
Configured onThe target group (path such as /health, interval, thresholds, expected status code)The container definition in the task definition (healthCheck)
How it checksHTTP request from the ALB to task-IP:8000/healthA command in the container, e.g. ["CMD-SHELL", "curl -f http://localhost:8000/health || exit 1"]. Exit 0 = healthy
What it provesTraffic can reach the task and gets a good reply: port, security groups and app all line upThe process inside is OK, even when nothing sends it traffic
Startup allowancehealthCheckGracePeriodSeconds on the servicestartPeriod on the check itself (0 to 300 s, off by default)
Exists forOnly services behind a load balancerAny task, including workers and sidecars

Container check defaults: interval 30 s, timeout 5 s, retries 3.[12] With both defined, a new task counts as healthy during a deployment only when it passes both (section 2).

  • When the container check is the only one you have: a queue worker like lesson 7's solve worker has no load balancer, so the ALB check doesn't exist for it. A container check (e.g. "has the worker loop updated a heartbeat file in the last minute?") is how ECS finds out the worker is stuck.
  • A common gotcha: the command runs inside your image. Slim Python images often don't include curl, so the check fails on a perfectly healthy app. Use a tool that's actually in the image, e.g. python -c with urllib.
  • Why the ALB check fails when the container check passes: usually the network, not the app. For example, the task's security group doesn't allow the ALB's security group in on port 8000 (lesson 3), or the target group's port or path is wrong.

Follow-up: is a container check only for APIs with /health? Do I build it into the app? It's any command that exits 0 for healthy, so it doesn't need HTTP. It's optional: with no healthCheck, ECS just doesn't check. But yes, you design it as part of the app, because the app has to give the check something meaningful to look at, and the image has to contain whatever the command runs.

API:    reuse /health      ["CMD-SHELL", "curl -f http://localhost:8000/health || exit 1"]
Worker: heartbeat file     the loop touches /tmp/heartbeat on every pass
        ["CMD-SHELL", "python -c \"import os,time,sys; sys.exit(time.time()-os.path.getmtime('/tmp/heartbeat') > 300)\""]

Make the threshold longer than your slowest job (here 5 minutes for solves of up to 4), or a busy worker looks stuck. And keep the check shallow: test "this process can do work" (model loaded, loop alive), not "the database answers". If /health fails whenever RDS has a blip, every task fails at once and ECS replaces them all, turning a small outage into a big one.[13]
