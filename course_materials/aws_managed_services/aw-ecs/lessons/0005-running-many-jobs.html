Running many jobs

Scenario Lab: 200 what-if MILPs against a baseline, without blowing your quota or losing results

Your win for this lesson (about 30 minutes) You can pick the right shape for running many jobs (a RunTask loop, a Step Functions Map, or an SQS worker service), work out a safe concurrency from your Fargate vCPU quota, run the scenarios on Spot with retries that can't corrupt results, and collect everything into one baseline-vs-scenario comparison.

Warm-up

From lessons 2 to 4. Answer from memory before you click.

1 · The job: one Scenario Lab run

A planner asks: "What if the Dallas DC loses 20% capacity, lead times from Supplier B double, or we add a weekend shift?" The Scenario Lab turns that into 200 what-if MILPs, each a small change to tonight's baseline model. Every solve needs 4 vCPU / 16 GB and takes about 12 minutes. Afterwards, one comparison shows the planner how cost and service level move against the baseline.

Two rules carry over from earlier lessons:

  • One revision for the whole run. Baseline and all 200 scenarios use scenario-solver:5, so the only thing that differs is the input.
  • Inputs live in S3, not in overrides. Each scenario's changes are a JSON file at s3://scenario-lab/runs/<run_id>/scenarios/<id>.json. The task only gets two short environment variables, RUN_ID and SCENARIO_ID, which stay far below the 8,192-character limit.

2 · Three shapes for "many jobs"

ShapeHow it worksGood forBreaks down when
A. RunTask loopA script calls RunTask once per scenarioA handful of jobs, a quick experimentYou need concurrency limits, retries, "tell me when all are done", or a record of what failed. You'd be writing all of that yourself.
B. Step Functions MapA state machine loops over the scenario list, starts each task and waits for it to finishA batch with a known end: "run these 200, then compare"Work arrives all day in no fixed batch
C. SQS + worker serviceThe API puts one message per scenario on a queue. A service of long-running workers pulls and solves them.A steady stream of ad-hoc requests from many plannersYou need a single "everything finished" moment (you can build one, but it takes extra work)
Why count=10 doesn't help here RunTask can start up to 10 tasks in one call,[1] but they are 10 identical copies with the same overrides. Ten different scenarios need ten different SCENARIO_IDs, which means ten separate calls (or a queue that hands each worker a different message).

The Scenario Lab run is a batch with a clear end and a comparison step afterwards, so this lesson uses shape B. Shape C is the right fit for the interactive "submit a what-if any time" API. Lesson 6 covers it, along with scaling a service on queue depth.

3 · How many at once? Your quota decides

Fargate's main limit is the number of vCPUs running at the same time in an account and Region, with separate quotas for On-Demand and Spot. The default On-Demand quota for new accounts is 6 vCPU. It's adjustable, and Fargate also raises it automatically as your usage grows.[2][3] There's also a launch rate limit: Fargate's RunTask is limited to 20 calls per second.[4]

max at once  =  ( vCPU quota  −  vCPU already used by other things )  ÷  vCPU per task

Example (Spot quota raised to 120 vCPU, nothing else on Spot):
             =  ( 120 − 20 headroom ) ÷ 4  =  25 scenarios at once

Wall-clock   ≈  200 scenarios ÷ 25 at once × 12 min  ≈  96 min      (sequential: 40 hours)
The day-one trap On a new account with the 6-vCPU default, only one 4-vCPU scenario fits at a time. The other launches get rejected, and if your retries keep hammering them, the run is slow and noisy. Before the first real run, check the quota in the Service Quotas console and request an increase. Leave headroom too: the vCPUs your forecast API service uses come out of the same On-Demand pool.

4 · The state machine, piece by piece

A Map state runs the same steps once for each item in a list. In Inline mode it runs up to 40 iterations at once. Distributed mode runs each iteration as a child workflow and goes up to 10,000 in parallel. You need Distributed if you want more than 40 at once, if the execution history would pass 25,000 events, or if the input is bigger than 256 KiB.[5] At 25 concurrent and 200 items, Inline is enough.

Read it the way you read the task definition in lesson 2: say what each highlighted part does, then click.

{
  "QueryLanguage": "JSONata",
  "StartAt": "RunScenarios",
  "States": {
    "RunScenarios": {
      "Type": "Map",
      "Items": "{% $states.input.scenarios %}",
      "MaxConcurrency": 25,
      "ItemProcessor": {
        "ProcessorConfig": { "Mode": "INLINE" },
        "StartAt": "SolveScenario",
        "States": {
          "SolveScenario": {
            "Type": "Task",
            "Resource": "arn:aws:states:::ecs:runTask.sync",
            "Arguments": {
              "Cluster": "scenario-lab",
              "TaskDefinition": "scenario-solver:5",
              "CapacityProviderStrategy": [{ "CapacityProvider": "FARGATE_SPOT", "Weight": 1 }],
              "NetworkConfiguration": { "AwsvpcConfiguration": {
                "Subnets": ["subnet-private-a", "subnet-private-b"],
                "SecurityGroups": ["sg-scenario-worker"], "AssignPublicIp": "DISABLED" } },
              "Overrides": { "ContainerOverrides": [{ "Name": "solver", "Environment": [
                { "Name": "RUN_ID",      "Value": "{% $states.context.Execution.Name %}" },
                { "Name": "SCENARIO_ID", "Value": "{% $states.input.id %}" } ] }] },
              "StartedBy": "{% $states.context.Execution.Name %}"
            },
            "Output": "{% { 'id': $states.input.id, 'status': 'OK' } %}",
            "Retry": [
              { "ErrorEquals": ["ECS.AmazonECSException", "AmazonECS.Unknown"],
                "IntervalSeconds": 30, "BackoffRate": 2, "MaxAttempts": 5 },
              { "ErrorEquals": ["States.TaskFailed"], "IntervalSeconds": 60, "MaxAttempts": 2 }
            ],
            "Catch": [{ "ErrorEquals": ["States.ALL"], "Next": "RecordFailure",
              "Output": "{% { 'id': $states.input.id, 'status': 'FAILED',
                             'error': $states.errorOutput.Error } %}" }],
            "End": true
          },
          "RecordFailure": { "Type": "Pass", "End": true }
        }
      },
      "Next": "CompareToBaseline"
    },
    "CompareToBaseline": {
      "Type": "Task",
      "Resource": "arn:aws:states:::ecs:runTask.sync",
      "Arguments": { "Cluster": "scenario-lab", "TaskDefinition": "scenario-compare:2",
        "CapacityProviderStrategy": [{ "CapacityProvider": "FARGATE", "Weight": 1 }],
        "NetworkConfiguration": { "…": "same as above" },
        "Overrides": { "ContainerOverrides": [{ "Name": "compare", "Environment": [
          { "Name": "RUN_ID", "Value": "{% $states.context.Execution.Name %}" } ] }] } },
      "End": true
    }
  }
}
Items: the list to loop over, e.g. [{"id": "dallas-cap-80"}, {"id": "supplierB-lt-x2"}, …]. Each item becomes $states.input inside one iteration. Keep items tiny (just IDs). The real parameters are in S3, and an Inline Map's input must stay under 256 KiB.[5]
MaxConcurrency: the number from section 3. At most 25 scenarios run at once. When one finishes, the next one starts. Leave it out and Step Functions runs as many as it can (up to 40 in Inline mode), which could easily exceed your vCPU quota.
runTask.sync: the .sync suffix means "start the task and wait until it stops" (the Run a Job pattern).[6] Under the hood, Step Functions creates an EventBridge rule to watch the task state change events from lesson 4.[7] If RunTask returns a non-empty failures list, the state fails with AmazonECS.Unknown, so the "always check failures" rule from lesson 4 is enforced for you. Without .sync, the state succeeds as soon as RunTask returns and the Map would "finish" while the solves are still running.
TaskDefinition: pinned to :5 for every iteration. This is the reproducibility rule from the warm-up. Note that Step Functions writes parameters in PascalCase (TaskDefinition, not taskDefinition).[7]
FARGATE_SPOT: scenarios are retryable and nobody is waiting on any single one, so they're good Spot candidates (cheaper, but can be interrupted). Section 5 shows what an interruption looks like.
Overrides: only two short IDs. The task uses them to find its input file and to decide where to write its result. Using the execution name as RUN_ID ties every task and file back to this one run.
StartedBy: the batch tag from lesson 4, so you can list all of this run's tasks.
Output: shrink what each iteration returns. By default, a .sync state returns the full task description, which is several KB. The Map gathers all 200 of them into one array, and that can go past Step Functions' 256 KiB payload limit and fail the run right at the end. Returning just {id, status} keeps it small.
Retry: two kinds of trouble. ECS.AmazonECSException covers launch problems such as "capacity is unavailable"[8] (plus AmazonECS.Unknown for a non-empty failures list). Retry those patiently, with backoff. States.TaskFailed covers a task that started and then failed, e.g. a Spot interruption. Retry that a couple of times. Check this on day one: the integration page doesn't spell out how the container's exit code maps to state failure. Run one deliberately failing scenario (exit 1) and look at the error name Step Functions reports before you rely on these rules.
Catch: the most important line. Without it, one scenario that keeps failing (say, an infeasible model your code exits 1 for) fails the whole Map, and Step Functions tries to stop all the other running tasks.[6] With it, that iteration is recorded as FAILED and the other 199 keep going.
CompareToBaseline: runs once, after every iteration has finished. It's on on-demand FARGATE because it's a single short step the planner is waiting for. It gets only RUN_ID and reads the scenario list and results from S3 itself. (Passing the Map's 200-item result through an override could hit the 8,192-character limit.)

5 · Spot interruptions and retries that can't corrupt results

When Fargate needs Spot capacity back, your task gets a two-minute warning, delivered both as a task state change event and as SIGTERM to the container. The stopped task shows stopCode: TerminationNotice and stoppedReason: "Your Spot Task was interrupted." You can set stopTimeout up to 120 seconds to make full use of the warning. Also, Fargate doesn't swap in on-demand capacity when Spot runs short. Spot tasks just wait longer.[9]

Make every scenario idempotent

A retry runs the same scenario again. Design it so running twice gives the same final state as running once:

  • The output key depends only on the run and scenario: runs/<run_id>/results/<id>.json. A retry overwrites the same file instead of adding a second one.
  • Write the result last, in a single PUT. A half-finished solve leaves no result file rather than a misleading one.
  • Exit 0 only after that write succeeds (the contract from lesson 4).

Use the two minutes

  • Catch SIGTERM in Python (signal.signal(signal.SIGTERM, …)), tell the solver to stop, and exit.
  • For a 12-minute solve, starting over is fine. For a 3-hour solve, save the best solution found so far (the incumbent) to S3 every few minutes, and pass it as a warm start on the retry.
  • If a scenario keeps getting interrupted, add a final fallback: a Catch path that re-runs it on FARGATE on-demand.

6 · Collecting the results

The compare task does three things: it loads the baseline, loads every results/<id>.json, and reconciles them against the manifest. Any scenario that's listed but has no result shows up as MISSING in the comparison instead of quietly disappearing. That reconciliation is your second line of defence, after the Catch. Then it writes the delta table and (via SNS, as in lesson 4) tells the planner the run is ready.

Practice

Your questions from this session

Try to answer each one out loud before opening it.

300 scenarios at the same time: why isn't raising MaxConcurrency enough?

Because Inline mode has a hard ceiling of 40 concurrent iterations. MaxConcurrency can only set a limit under that ceiling, never above it. Set it to 300 and you still get at most 40 at once.[5]

Inline Map        ceiling 40         each iteration runs inside the parent workflow
Distributed Map   ceiling 10,000     each iteration is its own child workflow
MaxConcurrency    your limit, always ≤ the mode's ceiling
  • What changes: "ProcessorConfig": { "Mode": "DISTRIBUTED", "ExecutionType": "STANDARD" }, then MaxConcurrency: 300. The iteration steps (runTask.sync, Retry, Catch) stay the same.
  • The other half of the answer: 300 × 4 vCPU = 1,200 vCPU of Spot quota, plus headroom. The state machine change does nothing if the quota stays at 120.
  • A bonus of Distributed: each child workflow has its own execution history, so you also stay clear of the 25,000-event history limit. And it can read the scenario list straight from S3 instead of passing it in.
  • Why the wrong answers fail: count=10 gives identical copies (same overrides). Splitting into 8 Parallel branches means 8 Inline Maps to keep in sync by hand, which is a workaround for exactly what Distributed mode already does.

Rule of thumb: whenever you need more than 40 at once, the answer is Distributed mode, never a bigger number on Inline.
