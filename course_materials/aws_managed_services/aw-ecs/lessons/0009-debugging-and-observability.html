Debugging and observability

When a task won't start, or starts and misbehaves: where the evidence is, and how to read it

Your win for this lesson (about 25 minutes) Given the error from a stopped task, you can name the most likely cause and where to look next, without guessing. You also know how to see inside a running task when the logs aren't enough.

Warm-up

From lessons 4 to 8. Answer from memory before you click. Read each question carefully.

1 · Ask "did my code run?" first

You know the task lifecycle from lesson 4. Each stage leaves evidence in a different place, so the first question is always: how far did the task get?

How far did it get?Look at
A service can't start tasks at allThe service's events (the console's Events tab, or describe-services). A healthy service ends with "has reached a steady state".
Started, stopped before your code ranThe stopped task's stopCode and stoppedReason (section 3)
Your code ran and exitedThe container's exit code, then its logs (section 2)
Running, but slow or wrongMetrics (section 5), then a shell inside it with ECS Exec (section 6)

A standalone task (like the planner) has no service events, so go straight to the stopped task.[1]

2 · Logs: what your code printed

App: the inference API with an OTel collector sidecar. Whatever a container writes to stdout and stderr goes to CloudWatch Logs through the awslogs driver. The execution role does the sending (lesson 2). Explain each part, then click.

"logConfiguration": {
  "logDriver": "awslogs",
  "options": {
    "awslogs-group": "/ecs/inference-api",
    "awslogs-region": "eu-west-2",
    "awslogs-stream-prefix": "ecs",
    "mode": "non-blocking",
    "max-buffer-size": "25m"
  }
}
Log group: one per app is a good habit. Set a retention period on it, or logs are kept forever and you keep paying for them.
Stream prefix: each container in each task gets its own stream, named ecs/<container name>/<task ID>. That's how you find one task's logs: take the task ID from the stopped task and open the matching stream. On Fargate, the prefix is required.
Delivery mode: if CloudWatch can't keep up, should your app wait, or should logs be dropped? blocking makes writes to stdout wait, which can freeze the app until its health check fails. non-blocking keeps logs in a memory buffer and drops them if it fills. Since June 2025, non-blocking is the default: ECS chose availability over completeness.[2] AWS's tests suggest a 25 MB buffer.[3]

3 · Reading a stopped task

The nightly MILP planner didn't produce a plan. Its stopped task, from aws ecs describe-tasks (shortened):

{
  "lastStatus": "STOPPED",
  "stopCode": "TaskFailedToStart",
  "stoppedReason": "ResourceInitializationError: unable to pull secrets or registry auth:
    execution resource retrieval failed: unable to retrieve secret from asm: …
    AccessDeniedException: … is not authorized to perform: secretsmanager:GetSecretValue …",
  "containers": [{
    "name": "planner",
    "lastStatus": "STOPPED"
  }]
}
stopCode: the broad category. TaskFailedToStart means it never reached your code. Compare EssentialContainerExited (your code ran, then the essential container stopped) and SpotInterruption (lesson 5).
stoppedReason: the detail. It starts with an error category, here ResourceInitializationError, and the rest says what failed: the execution role isn't allowed to read the secret (lesson 8). ECS lists the categories, each with its own troubleshooting page.[4]
No exitCode: the container never started, so there's nothing to exit with, and no log stream either. When your code did run, each container shows an exitCode here (0, 1, 137, 143 from lesson 4).
Stopped tasks disappear after about an hour describe-tasks and the console show stopped tasks for only about an hour.[5] The planner fails at 02:00; you look at 09:00; it's gone. Fix: turn on event capture in the cluster's settings. ECS then keeps task and service events for a retention period you choose, in an Event History tab you can filter by stop code or exit code.[6] It's the same task state change events you sent to SNS in lesson 4.

4 · The "won't start" playbook

Most failures fall into a handful of patterns, and you've met every cause in an earlier lesson. Match the text, then check the place in the last column.

On a service, repeated failures like these trip the deployment circuit breaker (lesson 6), so you'll often first notice them as a failed deployment.

5 · Container Insights: metrics

When a task is running but slow, you need numbers. Container Insights is a cluster setting, containerInsights, with three values: disabled, enabled and enhanced. It collects CPU, memory, disk and network use for the cluster, each service and each task. enhanced (released December 2024) adds per-container detail and curated dashboards, and AWS recommends it.[8] It costs extra (CloudWatch pricing).

  • It's where RunningTaskCount comes from: your queue workers' scaling needs it (lesson 7).
  • Use it to size tasks. If the inference API's memory creeps up through the day and tasks die with 137 every evening, you've found a leak, or a task that's too small.
  • It reports only tasks that are RUNNING. A task that never starts sends no metrics, so for "won't start", go back to section 3.[8]

6 · Inside a running task: ECS Exec

The inference API is running and healthy, but traces never arrive. Is the app sending to the collector at all? You want a shell inside the task to check. There's no SSH on Fargate, and you don't open inbound ports. ECS Exec gives you a shell through AWS Systems Manager, with no ports to open and no keys to manage.[9]

aws ecs update-service --cluster ml --service inference-api \
  --enable-execute-command --force-new-deployment

aws ecs execute-command --cluster ml --task 3f9c… \
  --container app --interactive --command "/bin/sh"

# inside the app container
curl -s localhost:13133      # is the collector's health endpoint answering?
Turn it on: it's off by default, and only new tasks get it. That's why --force-new-deployment is there: the running tasks are replaced by ones with Exec enabled.[9] For a standalone task, pass --enable-execute-command to run-task.
Run a command: pick the task and, since there are two containers, the container. You need the Session Manager plugin installed on your own machine. Inside the task, the SSM agent needs the task role (not the execution role) to have the ssmmessages permissions, and a private subnet with no NAT needs an ssmmessages VPC endpoint (lesson 3 again).[9]
Inside: the containers in a task share localhost (lesson 1), so from the app container you can test the sidecar directly. 13133 is the OTel collector's usual health-check port. Your shell runs as root, sessions end after 20 idle minutes, and each ExecuteCommand is recorded in CloudTrail.[9]
Not everywhere: the agent code sandbox The agent code sandbox runs untrusted, LLM-written code, so it's locked down. ECS Exec needs a writable root filesystem (it doesn't work with readonlyRootFilesystem) and a task role with extra permissions, and both weaken that lockdown.[9] Leave it off there, and debug from logs. Treat Exec as a break-glass tool, turned on where you need it.

Bringing a dead sidecar back

Remember the warm-up: a crashed non-essential collector leaves the API serving with no telemetry, and nothing looks wrong. A container restart policy lets ECS restart just that container, without replacing the task. It works for essential and non-essential containers.[10]

"restartPolicy": {
  "enabled": true,
  "ignoredExitCodes": [0],
  "restartAttemptPeriod": 300
}

ignoredExitCodes: exits that shouldn't trigger a restart. A clean exit (0) isn't a crash. By default, every exit code triggers one. restartAttemptPeriod: how long the container must have run before ECS will restart it, from 60 to 1,800 seconds (default 300).

The attempt period stops restart loops: a container that crashes within its first 300 seconds isn't restarted, because that points to a real bug, not a passing glitch.[11]
