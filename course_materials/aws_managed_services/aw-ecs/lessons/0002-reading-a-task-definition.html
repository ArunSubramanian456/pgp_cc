Reading a Fargate task definition

field by field, using a nightly MILP planner

Your win for this lesson (about 20 minutes) You can read any Fargate task definition and say what every field does. You'll also be able to tell the two IAM roles apart, which is the mistake behind a large share of "my task won't start" and "AccessDenied" errors.

The app: a nightly replenishment planner

Every night at 1am, a MILP decides how much of each SKU to order for each distribution centre over the next 12 weeks. It reads demand forecasts and inventory from S3, solves with HiGHS, writes the plan back to S3, and exits. This is idea #4 from your idea bank.

From lesson 1, you already know two things about it:

  • It runs, finishes and exits, so it's a task, not a service. A service would restart it all day.
  • The JSON below is its task definition: the blueprint every nightly run is stamped from.

AWS's reference splits a task definition into the family, IAM roles, network mode, container definitions, volumes and capacity. Only family and containerDefinitions are always required.[1] On Fargate, a few more become mandatory: networkMode must be awsvpc, and task-level cpu and memory are required.[1]

Read it in two layers

A task definition has two layers:

  • Task level (the outer part): how big is the box, what's it called, and what is it allowed to do?
  • containerDefinitions (the inner part): what runs inside the box? This is the part that looks like a docker run command.

Before clicking anything, try to say out loud what each highlighted field does. Then click it to check.

family: the name of the blueprint. Each registration gets the next revision number, so this one becomes replenishment-planner:1, then :2, and so on. Required.[1]
requiresCompatibilities: tells ECS to check, at registration time, that every parameter you used is valid on Fargate. If it isn't, registration fails straight away, for example if you ask for a GPU.[1] It's better to fail at registration than at 1am.
networkMode: on Fargate this must be awsvpc, which gives each task its own network interface.[1] Lesson 3 is about what this means for subnets and security groups.
runtimePlatform: the OS family and CPU architecture. The defaults are LINUX and X86_64. Linux tasks can also use ARM64.[1] Your image must be built for whichever architecture you choose.
cpu / memory: the size of the whole task. Both are required on Fargate and must be a valid pair.[2] 8192 CPU units = 8 vCPU, which allows 16 to 60 GB in 4 GB steps, so 32768 MiB (32 GB) is valid. A MILP with a big branch-and-bound tree is usually memory-hungry, so size memory for your largest instance. Note that SOLVER_THREADS = 8 matches the 8 vCPUs.
ephemeralStorage: scratch disk. Fargate gives at least 20 GiB by default, and you can raise it to 200 GiB. Your container image is stored on the same disk, and the disk is wiped when the task stops.[3] That's why the plan goes to S3, not /tmp.
executionRoleArn: used by ECS/Fargate to get the task started. It pulls the private ECR image, sends logs to CloudWatch and fetches the secrets. Its credentials "aren't directly accessible by the containers in the task."[4]
taskRoleArn: used by your Python code. When boto3 reads forecasts from S3 or writes the plan, it uses this role's permissions.[1] Give each app its own role with only what it needs.
containerDefinitions: the list of containers in the task. There's just one here, because this job doesn't need a sidecar (lesson 1). Required.
name: the container's name inside the task. It appears in log stream names and in error messages.
image: your Docker image in ECR. It has an explicit tag (2026.10.1), not latest, so every night runs exactly the code you think it runs. This also matters for your Scenario Lab baselines.
essential: if an essential container stops, ECS stops every other container in the task. If you leave this out, the container counts as essential, and every task needs at least one essential container.[1] You'd set false on a sidecar the app can survive without.
command: the command the container runs, replacing the image's CMD. It's the same as the COMMAND part of docker run.[1] Each argument goes in its own string.
environment: plain environment variables, the same as docker run -e. Use them for configuration, never for passwords, because anyone who can read the task definition can see them.
secrets: when the task starts, ECS fetches the value from Secrets Manager (or SSM Parameter Store) and sets it as DB_PASSWORD. The task definition only holds the ARN. Fetching the value is the execution role's job.[4] The :password:: ending picks one key out of a JSON secret.
logConfiguration: awslogs sends your container's stdout and stderr to CloudWatch Logs. Group and region are required, and on Fargate the stream prefix is required too. Streams are named prefix/container-name/task-id.[5] Your solver's progress logs end up here.
stopTimeout: when the task is stopped, ECS waits this many seconds for the container to exit on its own before killing it. The default is 30 and the maximum is 120.[1] Handle the stop signal (SIGTERM) in your solver so it saves its best solution so far to S3 in that window. This comes up again with Fargate Spot.
No portMappings: nothing ever calls this job. It reaches out to S3 and nothing connects in. A forecast API would map a port, such as 8000 for FastAPI. Leaving out a field you don't need is a design decision too.

Your questions from this session

What are the networkMode options? Is awsvpc the default VPC? Can I use my own private VPC and subnets?

There are four modes. If you set none, the default is bridge, but Fargate requires awsvpc.[8]

ModeWhat happensWhere allowed
awsvpcEach task gets its own network interface, private IP and security groups, as if it were its own little server.Fargate (only option), EC2, Managed Instances
bridgeTasks share the host's interface through a virtual Docker bridge (like Docker on your laptop).EC2 Linux only
hostContainers sit directly on the host's network, with no isolation.EC2, Managed Instances[9]
noneNo external networking.EC2 Linux

awsvpc is not "the default VPC". It's a mode, meaning "give this task its own network interface in a VPC". Which VPC isn't in the task definition at all. You choose it when you run the task or create the service, in networkConfiguration: a list of subnets (all in one VPC), security groups and assignPublicIp. It's required for awsvpc.[10] So yes, use your own VPC and private subnets. That's the normal production setup.

Task definition:   "networkMode": "awsvpc"            ← the HOW
RunTask / service: networkConfiguration.awsvpcConfiguration = {
                     subnets:        [private-a, private-b],
                     securityGroups: [sg-planner],
                     assignPublicIp: DISABLED }      ← the WHERE

One catch: a task still needs a network path to ECR (to pull its image), CloudWatch and S3. In a public subnet it needs a public IP.[2] In a private subnet it needs a NAT gateway or VPC endpoints. That's lesson 3.

My Dockerfile already has CMD. Why repeat it in the task definition?

You don't have to. command is optional. If you leave it out, the container runs the image's CMD. If you set it, it replaces CMD, just like adding a command to the end of docker run.[1] (entryPoint does the same for ENTRYPOINT.)

Reasons to set it anyway:

  • One image, several jobs. The same replenishment-planner image can be planner.solve in one task definition and planner.validate_inputs in another, or an API and a queue worker built from one codebase.
  • Visible in one place. Whoever reads the task definition sees exactly what runs, without opening the Dockerfile.
  • Per-run arguments. RunTask can override command for a single run, e.g. --horizon-weeks 26.[10]
How does ECS pass environment variables to my container? And how do I run 200 scenarios by changing them?

How it works: when ECS creates the container, it hands the variables to the container runtime, the same as docker run -e KEY=value. Your code just reads os.environ["SOLVER_THREADS"]. If the same name is set in more than one place, the most specific one wins:

run-time override  >  task definition "environment"  >  Dockerfile ENV

For 200 scenarios, don't edit the task definition 200 times. That would register 200 revisions, and none of them would be your baseline. Keep one pinned revision and call RunTask 200 times, each with an environment override. Overrides can change existing variables or add new ones.[10]

import boto3
ecs = boto3.client("ecs")

for sc in scenarios:   # e.g. {"id": "demand_x1.2_dc3_cap-30"}
    ecs.run_task(
        cluster="planning",
        taskDefinition="replenishment-planner:3",      # pinned = same code+settings as baseline
        launchType="FARGATE",
        networkConfiguration={"awsvpcConfiguration": {
            "subnets": PRIVATE_SUBNETS, "securityGroups": [SG_PLANNER],
            "assignPublicIp": "DISABLED"}},
        overrides={"containerOverrides": [{
            "name": "solver",                           # must match the container name
            "environment": [
                {"name": "SCENARIO_ID", "value": sc["id"]},
                {"name": "SCENARIO_S3", "value": f"s3://acme-scenarios/batch-42/{sc['id']}.json"},
            ]}]},
        startedBy="scenario-batch-42",                 # lets you list this batch's tasks later
    )

Two design rules come from limits in the API:

  • Pass a pointer, not the data. All overrides together are limited to 8,192 characters, JSON included.[10] Put the scenario's demand multipliers and constraint toggles in an S3 JSON file, and pass only its key.
  • Tag the batch. startedBy (up to 128 characters) lets you find every task in batch 42 afterwards.[10]

Firing 200 eight-vCPU tasks at once can also hit your account's Fargate vCPU quota. That's why Scenario Lab will later use a queue or Step Functions to limit how many run at a time.

What is stopTimeout actually for? When does it apply?

Yes, it's wrap-up time. When ECS stops a task, it sends each container SIGTERM ("please shut down"). If the container hasn't exited after stopTimeout seconds (default 30, max 120), it sends SIGKILL, which kills it instantly with no cleanup.[11] In that window your code can save its best solution so far, flush logs, or finish in-flight requests.

It applies whenever ECS stops a task, not only when you do it by hand:[12]

  • you call StopTask or click Stop in the console
  • a deployment replaces old tasks with a new revision
  • scale-in, when autoscaling goes from 4 tasks to 2
  • a Fargate Spot interruption (2-minute warning)
  • the task's essential container stops, so ECS stops the other containers

It doesn't apply when your process finishes and exits on its own. Your nightly solve completing normally needs no stop signal. And if the process is killed some other way, for example it runs out of memory, there's no graceful window.

For a service behind a load balancer, ECS first removes the task from the load balancer, so it gets no new requests, then sends SIGTERM.[12]

import signal, sys
def on_sigterm(signum, frame):
    save_incumbent_to_s3()      # best feasible plan so far + MIP gap
    sys.exit(0)
signal.signal(signal.SIGTERM, on_sigterm)

Since 120 seconds is the ceiling, a 40-minute MILP can't wait for a stop to finish the solve. It has to checkpoint and exit quickly.[12]

Network modes in plain English: what do bridge, host and none actually mean?

Picture an EC2 server as an apartment building and each task as a flat. Example: two copies of your forecast API on one server, both listening on port 8000.

awsvpc  every flat has its own street address
        10.0.1.15:8000 → copy 1     10.0.1.16:8000 → copy 2     (own security group each)

bridge  one building address + a mailroom that forwards
        10.0.1.10:32768 → copy 1:8000    10.0.1.10:32769 → copy 2:8000   (one SG for the building)

host    no flats, everyone stands in the lobby
        10.0.1.10:8000 → copy 1     10.0.1.10:8000 → copy 2  ✗ port already taken

none    a flat with no doors or windows: only localhost
  • bridge is Docker-on-your-laptop style (-p 32768:8000). Tasks share the server's IP and security groups. ECS can pick a random outside port (a dynamic port).[13]
  • host is fast, but with port mappings you can't run two copies of the same task on one server.[8]
  • On Fargate there's no building you manage, so it's always awsvpc. You only need to recognise the others in older tutorials and EC2 setups. A hint: hostPort or dynamic ports means it's bridge.
What is RunTask?

The ECS API action that "starts a new task using the specified task definition".[10] It's the "run this once, now" button, and it's how standalone tasks start. You can call it from the console (Run new task), the CLI (aws ecs run-task …), boto3 (ecs.run_task(…)), or other services such as EventBridge Scheduler (nightly) and Step Functions (fan-out).

  • RunTask: start it now, it runs until it exits, and nobody restarts it. Use it for the planner, retraining and scenarios.
  • CreateService: keep N running forever, replacing any that stop. Use it for the forecast API.

It gets its own lesson after networking: scheduling, fan-out and concurrency.
