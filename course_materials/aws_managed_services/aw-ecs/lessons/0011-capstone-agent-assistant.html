The brief

"Ask the data": an agentic data-exploration assistant

A mid-size distributor's 60 supply chain planners ask questions in plain English, like "why did DC-North stock out of SKU 4471 last week?" or "plot forecast vs actuals for the top 20 SKUs". A chat web app sends each message to your assistant API, which runs an agent loop:

  • calls Claude on Amazon Bedrock to plan and write answers;
  • queries the planning database, a Postgres read replica on RDS in a private subnet;
  • calls a third-party web search API (on the internet, needs an API key) for things like supplier news;
  • runs Python analysis code that the LLM writes (pandas, plotly) to compute numbers and draw charts. This code is untrusted. A run takes up to 2 minutes and needs about 1 vCPU and 2 GB;
  • saves conversations and generated charts to S3.

Traffic: business hours in one time zone, a clear peak on Monday mornings. A chat reply takes 10 to 40 seconds, mostly waiting on the LLM, so CPU stays low. Roughly 600 code runs a day.

Constraints: the data is commercially sensitive and must never be reachable from the internet. The team is two data scientists, with no dedicated ops person. They ship a new version weekly and don't want to drop chats in progress when they do. Budget-conscious. Region eu-west-2. No GPUs needed.

Part 1: How does the frontend send a user's message to the API? Shouldn't the frontend be in a public subnet?

Only the ALB is public. Every task, frontend included, sits in a private subnet with no public IP. The ALB is the one public door, and it reaches its targets on private IPs (lesson 3). "This container serves web pages" doesn't make it public.

How the message travels depends on where the frontend's code runs:

A · Browser-side frontend (React, Vue: JavaScript running in the planner's browser)
    The frontend service only hands out HTML and JS files. The BROWSER calls the API:
    browser ──▶ public ALB ──/──────▶ frontend tasks   (page files)
    browser ──▶ public ALB ──/api/*─▶ api tasks        (chat messages)
    The frontend container never sees a chat message. That's the /api/* path rule.

B · Server-side frontend (Streamlit, Gradio, Django, Next.js server)
    The frontend's SERVER receives the message and calls the API itself, inside the VPC:
    browser ──▶ public ALB ──▶ frontend tasks ──Service Connect──▶ api tasks
                                 (private)       (or an internal ALB)  (private)

In B, the frontend needs a stable address for the API, because API tasks come and go, and their IPs change with them. Two ways to get one:

  • ECS Service Connect (AWS's recommendation): the frontend just calls http://assistant-api:8000. ECS adds a small proxy container to each task that finds healthy API tasks and spreads requests across them, and it reports traffic metrics. No extra load balancer to pay for.[1]
  • An internal ALB: a load balancer in private subnets with no public address. It works too, but it's one more thing to run and pay for.

Either way, the security group is the permission, not the route: the API's group allows the frontend's group on port 8000. Traffic flows on private IPs inside the VPC, with no NAT involved.

Most data-science chat UIs (Streamlit, Gradio) are case B.

Follow-up: is "only the ALB is public" an ECS rule? No, it's the recommended pattern, not something ECS enforces. You can give a task a public IP in a public subnet (lesson 3's cheapest way out, with no NAT), and it would work. The guide is: only what must be reachable from the internet, or must reach it directly, goes in public subnets. That's an internet-facing ALB and the NAT gateway itself. Everything else (frontend, API, workers, sandbox, database, internal ALB) goes in private subnets.

Part 1: How would a "pool of sandbox workers fed from a queue" work, step by step?

It's the lesson 7 solve worker, running code instead of a MILP:

Setup: a sandbox-worker SERVICE (e.g. min 2, max 10) and an SQS queue "sandbox-jobs".

9. Auto scaling watches backlog per task and adds workers when runs pile up

A middle way: each worker runs one job, then exits. The service sees a task stop and starts a fresh one in the background, so a clean, warm worker is usually waiting. You get isolation like a task per run, with less of the waiting.

Part 1: How does the API start the sandbox task?

Through the ECS RunTask API. The CLI (aws ecs run-task) and boto3 (ecs.run_task(...)) are two clients of the same API. From the API's code:

resp = ecs.run_task(cluster="assistant", taskDefinition="sandbox:3",
    launchType="FARGATE", networkConfiguration={...private subnets, sandbox SG...},
    overrides={"containerOverrides": [{"name": "sandbox",
        "environment": [{"name": "RUN_ID", "value": run_id}]}]})
arn = resp["tasks"][0]["taskArn"]
ecs.get_waiter("tasks_stopped").wait(cluster="assistant", tasks=[arn])   # then check exitCode

Because the API's code makes the call, the permission goes on the API's task role: ecs:RunTask on the sandbox family, plus iam:PassRole for the sandbox's roles. That's Part 3.

What is Service Connect? (New: not covered in lessons 1 to 10)

The problem it solves: the frontend needs to call the API, but API tasks come and go (deployments, scaling, replacements), and each new task gets a new private IP. The frontend needs one name that always reaches a healthy API task.

What it is: an ECS feature that lets one service call another by a short name, like http://assistant-api:8000. ECS keeps the list of healthy tasks up to date and spreads requests across them.[4]

frontend task                                      assistant-api task
┌───────────────────────────┐                      ┌───────────────────────────┐
│ Streamlit                 │                      │ proxy  ──▶  FastAPI :8000 │
│   │ http://assistant-api:8000                    │   ▲                       │
│   ▼                       │   private IP, VPC    │   │                       │
│ proxy (added by ECS) ─────┼──────────────────────┼───┘                       │
└───────────────────────────┘                      └───────────────────────────┘

The proxy is a small container ECS adds to each task for you (a managed sidecar, lesson 1). It looks up which API tasks are healthy, picks one, retries around ones that fail, and reports request counts and errors as metrics.

Two settings:

// assistant-api task definition: give the port a name
"portMappings": [{ "name": "api", "containerPort": 8000, "appProtocol": "http" }]

// assistant-api SERVICE ("client-server": it can be called)
"serviceConnectConfiguration": { "enabled": true, "namespace": "assistant",
  "services": [{ "portName": "api",
                 "clientAliases": [{ "port": 8000, "dnsName": "assistant-api" }] }] }

// frontend SERVICE ("client": it only calls others)
"serviceConnectConfiguration": { "enabled": true, "namespace": "assistant" }

The namespace is the shared phone book both services join. ECS creates and manages it; treat it as a black box.[5]

  • Security groups still apply: the API's group must allow the frontend's group on 8000. Service Connect finds the tasks; security groups decide who may connect.
  • ECS services only: it connects services to each other. Your standalone sandbox tasks aren't in it, and the public ALB still handles internet traffic.
  • Changes take effect with a deployment: new settings reach new tasks, so turning it on means a new deployment of both services.
  • The proxy uses a little CPU and memory in every task. Leave room for it when sizing.

Part 2: Why do Bedrock, Secrets Manager, ECR and CloudWatch Logs need VPC endpoints? And does Postgres?

Postgres: no. RDS already lives inside your VPC, with private IPs in your private subnets. The API reaches it directly; the database's security group is the only gate. VPC endpoints are for AWS services that live outside your VPC.

The others: yes, because the tasks are in private subnets. Bedrock, S3, Secrets Manager, ECR and CloudWatch Logs are AWS APIs with public addresses. A task in a private subnet has no route to a public address unless you give it one:

Way outCoversNotes
NAT gatewayEverything: AWS APIs and the third-party APIsNeeded anyway for search/weather. Charged per hour and per GB through it, so big image pulls and chatty logs add up.
S3 gateway endpointS3 onlyFree. Always add it.
Interface endpointsOne AWS service each: ecr.api, ecr.dkr, logs, secretsmanager, bedrock-runtime…Charged per hour per AZ. Traffic stays on the AWS network. Required for any task with no NAT route.

Remember that on Fargate, pulling the image, fetching secrets and sending logs all go out through the task's own network interface, so they need a route too, and the task's security group must allow them.[6] For the API, NAT alone would work; endpoints keep the sensitive traffic off the internet path. For the sandbox, which should have no NAT route, the endpoints are the only way it can even start.

Part 2: Why does the sandbox need a security group if nothing connects to it?

Every Fargate task gets a security group, because each task has its own network interface. You're right that its inbound rules should be empty. The important part is outbound: a new security group allows all outbound traffic by default.

The sandbox runs code an LLM wrote, and an LLM can be tricked by a prompt into writing harmful code. With open outbound rules, that code could:

  • send your planning data to a server on the internet;
  • call the assistant API or other services inside the VPC;
  • try to reach the database (blocked only because the DB's group allows just the API's group).

Lock it down twice:

  1. Subnets: run the sandbox in separate private subnets whose route table has no NAT route, so there's no path to the internet at all.
  2. Outbound rules: allow only HTTPS (443) to the VPC endpoints it needs (ECR and Logs, to start and to log) and to S3 through the gateway endpoint. Nothing else.

One thing a security group can't block: the task's own credentials endpoint, which is how code inside any task gets its task role's credentials. That's why the sandbox's task role must be tiny (Part 3).

Part 2: What is the ALB's 60-second idle timeout, and why does it matter here?

A load balancer closes a connection if no data at all passes through it for 60 seconds (the default; you can set 1 to 4,000).[7] It doesn't matter that your code is still busy: the user just gets an error, and the work carries on with nobody waiting for it.

Why it matters for this app: a normal reply takes 10 to 40 seconds, which fits. A reply that includes a sandbox run doesn't: the task has to start, the code runs for up to 2 minutes, then the LLM writes the answer. That's easily 3 minutes with nothing sent back.

In your design (B), the long wait sits on the frontend → API call, which goes through Service Connect. That has its own timeouts (an idle timeout, 5 minutes by default for HTTP, and a per-request timeout), so check those too.[8] The public ALB still carries Streamlit's long-lived connection to each browser, so the 60-second timer applies there too.

The design fix: don't make one request wait minutes.

1. frontend → POST /runs          API starts the work, replies at once: {"run_id": "r-42"}
2. frontend → GET  /runs/r-42     every few seconds: {"status": "running"}  (UI: "Analysing…")
3. frontend → GET  /runs/r-42     {"status": "done", "answer": …, "chart": "s3://…"}

Every request is short, so no timeout is ever close, and a deployment or a lost connection doesn't lose the work: the run's status lives in S3 or a small table, not in an open connection. Streaming the reply (sending bytes as they're produced) also resets idle timers. Raising the timeout is the blunt fix: it works, but it keeps connections open for minutes during deployments (Part 4).

Part 2: The sandbox only runs Python. Why does it need endpoints at all?

Because the sandbox is a container, and a container needs its image. Two different things are involved:

The sandbox imageThe LLM's code
WhatPython, pandas, plotly, and your small "runner" scriptcode.py for one question
Built byYou, once per releaseThe LLM, for every run
Lives inECRS3: runs/{run_id}/code.py

Each RunTask starts a brand-new Fargate task, which pulls the image fresh. One run, step by step:

PENDING   pull the sandbox image        → ecr.api (log in, find the image)
                                          ecr.dkr (fetch the image manifest)
                                          S3      (the image's layers are stored there)
RUNNING   runner downloads code.py      → S3
          runs it, prints progress      → logs  (stdout to CloudWatch)
          uploads result.json           → S3
STOPPED   exits 0 or 1

That's all it needs: ECR, Logs and S3. No Secrets Manager, no Bedrock, no database, no internet. Without the ECR endpoints, the task never gets past PENDING.

Part 3: The recommended roles and secrets

Rule from lesson 2: the execution role is used by ECS to get the task going and keep it running around your code (pull the image, send logs, fetch secrets). The task role is used by your code for the AWS calls it makes itself.

DB host in environment
sandboxECR pull, write logsS3 GetObject/PutObject on runs/* onlyNone
  • Logs belong to the execution role: the awslogs driver sends them, not your code.
  • No S3 permission is needed to pull from ECR: ECR permissions cover the layers, even though they're stored in S3. S3 needs a network route (the gateway endpoint), not an IAM permission.
  • The database isn't an IAM permission: the API logs in with a username and password (a read-only user) over the network the security groups allow.
  • iam:PassRole: when the API calls RunTask, it hands the sandbox's roles to ECS. IAM checks that the API is allowed to pass those exact roles. Without it, RunTask fails with AccessDenied.
  • Rotation: force a new deployment after rotating, or read the secret at runtime (then the permission moves to the task role). For the DB password, rotate and redeploy together, or old tasks fail on new connections.

Part 3: What is iam:PassRole, and why does the API need it to call RunTask?

The idea: some AWS calls ask a service to go and do work while holding a role. RunTask is one: "ECS, start a sandbox task, and give it the sandbox's task role and execution role." Handing a role to a service is called passing it, and IAM checks it separately.

Why the check exists: without it, anyone allowed to start tasks could start one holding a more powerful role than their own, and run code that uses it.

API task role:  can run tasks, can't touch the database admin secrets
Attacker (a bug, or a prompt-injected agent) calls:
  RunTask sandbox:3  with an override  taskRoleArn = AdminRole
→ the new task holds AdminRole credentials → game over

iam:PassRole closes that gap: the caller may hand over only the roles listed. Analogy: you may lend a visitor a badge only if it's on your list of badges you're allowed to lend.

{ "Effect": "Allow", "Action": "ecs:RunTask",
  "Resource": "arn:aws:ecs:eu-west-2:111122223333:task-definition/sandbox:*" },
{ "Effect": "Allow", "Action": "iam:PassRole",
  "Resource": [ "arn:aws:iam::111122223333:role/sandbox-task-role",
                "arn:aws:iam::111122223333:role/sandbox-execution-role" ],
  "Condition": { "StringEquals": { "iam:PassedToService": "ecs-tasks.amazonaws.com" } } }
  • Both of the sandbox's roles are passed (task and execution), so both are listed.
  • Never "Resource": "*" for PassRole: that's exactly the escalation above.
  • The condition says these roles may be passed only to ECS tasks.
  • You've met this before: lesson 4's EventBridge Scheduler role needed iam:PassRole to start the nightly planner, for the same reason. So does whoever deploys a service.

Parts 5 to 8: The recommended scaling, images, observability and cost

5 · Scaling. The API has no ALB in front of it (Service Connect), so ALBRequestCountPerTarget isn't available for it. Scale it on requests per task from Service Connect's own metrics (RequestCount, published by the proxy)[9], or on a custom "active chats per task" metric. The frontend can use ALBRequestCountPerTarget. Both: min 2, a max you justify, and scheduled scaling that raises the minimum before Monday 08:00. The sandbox is standalone tasks, which have no desiredCount, min or max (scaling attaches only to services, lesson 7): cap concurrent runs in the API's code, and size the cap from demand and the vCPU quota. 600 runs × ~2.5 min over a ~9-hour day averages about 3 running at once, so a cap of 4 would queue at peaks; 8 to 10 is safer.

6 · Images. Three repositories (frontend, api, sandbox); IMMUTABLE; tags = date + git commit; task definitions name those tags. Lifecycle: expire untagged after 7 days + keep the newest 20 tagged builds. Never "anything older than 7 days" for tagged images: with weekly releases, that deletes the image a service is running, and the next scale-out fails with CannotPullContainerError (lesson 8). Enhanced scanning, especially for the sandbox. Build for ARM64 (or multi-arch) if you choose ARM.

7 · Observability. As your amended answer, plus: put conversation_id and run_id in every log line, and log how long each step takes (LLM call, SQL, sandbox start, sandbox run), so "it got slow" becomes "the sandbox start is slow". Store each run's task ARN with its run_id, so you can find its stopped reason and log stream. Set log retention.

Does ECS create the ALB for me? Can the task definition put the ALB in public subnets and the tasks in private ones?

No to both. The ALB is a separate resource (Elastic Load Balancing), and the task definition holds no subnets or load balancer settings at all. Three layers, three jobs (you saw the service part in lesson 3):

LayerNetworking it holds
Task definition (the blueprint)networkMode: awsvpc (how) and portMappings (8501). No subnets, no ALB.
ServicenetworkConfiguration: private subnets, security group, assignPublicIp: DISABLED (where the tasks go). loadBalancers: which target group to register tasks in.
ALB (separate resource)Scheme internet-facing, its own public subnets (2+ AZs), its own security group, an HTTPS listener with a certificate, and a target group of type ip.
"networkConfiguration": { "awsvpcConfiguration": {
    "subnets": ["subnet-private-app-a", "subnet-private-app-b"],
    "securityGroups": ["sg-frontend"], "assignPublicIp": "DISABLED" } },
"loadBalancers": [{ "targetGroupArn": "arn:…:targetgroup/frontend-tg/…",
                    "containerName": "streamlit", "containerPort": 8501 }]

The public/private split happens because the ALB and the service each get their own subnets, linked only by the target group. Who creates the ALB: you (console, aws elbv2, or infrastructure as code). Three shortcuts create one for you: the ECS console's create-service screen can, Express Mode does (lesson 10), and CDK's ApplicationLoadBalancedFargateService does. All three still build the same separate ALB.
