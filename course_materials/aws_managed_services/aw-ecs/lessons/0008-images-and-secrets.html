Images and secrets

Make a revision mean the same code every time, tidy up without breaking anything, and handle secrets that change

Your win for this lesson (about 25 minutes) You can set up an ECR repository so that a task definition revision always runs the same image, write a cleanup policy that can't delete an image a service still needs, and predict what happens to running tasks when a secret is rotated.

Warm-up

From lessons 6 and 7. Answer from memory before you click.

1 · Three IDs, three jobs

Your images live in Amazon ECR (Elastic Container Registry): one repository per image, like retrain or forecast-api. A task definition points at an image in one of two ways:

111122223333.dkr.ecr.eu-west-2.amazonaws.com/retrain:2026-10-24-a1b2c3d      by tag
111122223333.dkr.ecr.eu-west-2.amazonaws.com/retrain@sha256:4f9e…           by digest

Add the revision from lesson 1, and you have three different identifiers. Keep them apart:

IdentifierExampleNamesCan it change?
Revisionretrain-job:12The task definition (the blueprint)No. Changes make a new revision
Tag:2026-10-24-a1b2c3dA label on an image in ECRYes, by default. Push again with the same tag and the label moves to the new image
Digest@sha256:4f9e…The image's exact content (a hash of it)Never. Different content, different digest

So a revision is only as fixed as the image reference inside it. If that reference is a tag that can move, the same revision can run different code.

2 · The reused-tag trap

New app: the weekly forecast retraining job, a standalone task started every Monday (the lesson 4 shape). Its task definition, retrain-job:12, uses retrain:latest, and every week CI builds the newest code and pushes it as latest.

Then the forecasts drift, and you want to rerun last month's training exactly as it was. Same revision, same data, different model. Why?

A standalone task resolves the tag every time it starts. latest pointed at a different image each week, so retrain-job:12 has run four different versions of your code. Nothing in ECS remembers which one.

Services behave differently: they pin the digest

For a service, ECS resolves the tag once per deployment. The first task of the deployment pulls the image, ECS records its digest, and every later task in that service uses that digest, even if the tag has since moved. AWS calls this software version consistency.[1][2]

  • Good: when auto scaling adds tasks (lesson 7), they run exactly the same image as the tasks already there.
  • Surprising: push a fixed image as forecast:latest and the running forecast API doesn't change. To pick up what the tag now points at, you need a new deployment (Force new deployment, lesson 6).[3]
  • You can turn this off per container with "versionConsistency": "disabled". Don't, unless you have a good reason.[3]

The fix: tags that can't move

Turn on tag immutability for the repository, and give every build a unique tag (date plus git commit is a good habit). After that, pushing an existing tag fails with ImageTagAlreadyExistsException.[4] Explain each part, then click to check.

aws ecr create-repository --repository-name retrain \
  --image-tag-mutability IMMUTABLE_WITH_EXCLUSION \
  --image-tag-mutability-exclusion-filters filterType=WILDCARD,filter=dev-*

docker push 111122223333.dkr.ecr.eu-west-2.amazonaws.com/retrain:2026-10-24-a1b2c3d
Mutability setting: four choices. MUTABLE (the default) and IMMUTABLE apply to every tag. The two _WITH_EXCLUSION versions flip the rule for tags that match a filter.[4] Here: every tag is fixed for good, except the ones matched below. You can change this later with put-image-tag-mutability.
Exclusion filter: tags that match dev-* stay movable, so a developer can keep pushing dev-myfeature while testing. Anything you'd deploy or want to reproduce gets a tag that doesn't match.
A unique tag per build: the date tells a human when it was built, and the git commit says exactly which code is in it. Now retrain-job:12 → this tag → one digest is a chain that can't move. The same idea pinned the Scenario Lab baseline in lesson 5.
Rule of thumb Deploy and run only by immutable tags (or by digest). Then "which code ran?" is answered by the revision alone, for services and for standalone jobs.

3 · Cleaning up without breaking things

The retraining image carries PyTorch and is several gigabytes. One a week adds up, and ECR charges for storage. A lifecycle policy deletes ("expires") images by rule, so nobody has to clean up by hand.[5]

{ "rules": [
  { "rulePriority": 1,
    "description": "Clear untagged images after 7 days",
    "selection": { "tagStatus": "untagged",
                   "countType": "sinceImagePushed", "countUnit": "days", "countNumber": 7 },
    "action": { "type": "expire" } },
  { "rulePriority": 2,
    "description": "Keep the 20 newest weekly builds",
    "selection": { "tagStatus": "tagged", "tagPatternList": ["20*"],
                   "countType": "imageCountMoreThan", "countNumber": 20 },
    "action": { "type": "expire" } }
] }
rulePriority: rules run from the lowest number up, and each must be unique. A rule with "tagStatus": "any" must come last.[5]
Untagged, older than 7 days: images with no tag at all, such as the old image left behind when a movable dev-* tag moves on. sinceImagePushed counts age in days. Read the warning below before you trust this rule.
expire deletes the image. The other action, transition, moves it to cheaper archive storage instead, for images you might need again someday.[5]
Keep the newest 20 tags matching 20* (the weekly builds: 2026-10-24-…) and expire older ones. Notice what doesn't match: a baseline-2026-q3 tag for the Scenario Lab baseline. No rule selects it, so it's kept for good. That's how you protect an image you must be able to rerun.

How a cleanup breaks a scale-out

Lifecycle rules don't know what ECS is running. Combine a movable tag with section 2's digest pinning, and you get this:

The error you'd see names the tag and the missing digest, something like …/forecast:latest@sha256:…: not found.[3] The "keep newest 20" rule has a milder version of the same risk: a service that hasn't been redeployed in 20 builds. Keep the count well above how far back anything you run could be.

4 · Scanning: knowing what's inside

An ML image carries hundreds of packages you didn't write. ECR can scan images for known vulnerabilities (CVEs).[6] It's set for the whole registry, with filters for which repositories to scan.

Basic (the default)Enhanced
What it checksOperating system packagesOS packages and language packages (your numpy, scipy, torch)
WhenOn push, or when you start a scan by handOn push, or continuously: results update as new CVEs are published
Run byECRAmazon Inspector (a separate service, extra cost)

Scanning reports findings. It doesn't stop ECS from pulling the image: acting on findings is your job (or your CI pipeline's, which is out of scope for now).

5 · Secrets, one level deeper

Recap from lesson 2: environment is for plain config; secrets holds only an ARN, and the execution role fetches the value when the task starts. Now the details that bite. App: the agentic data-exploration assistant, which uses an LLM on Bedrock, a third-party web search API and a Postgres database.

The best secret is no secret The agent calls Bedrock with the task role: AWS gives it temporary credentials, so there's no key to store, leak or rotate. Only the search API (not AWS) and the database password need secrets. 
"environment": [
  { "name": "MODEL_ID",  "value": "anthropic.claude-…" },
  { "name": "LOG_LEVEL", "value": "INFO" } ],
"secrets": [
  { "name": "SEARCH_API_KEY",
    "valueFrom": "arn:aws:secretsmanager:eu-west-2:111122223333:secret:agent/search-AbCdEf" },
  { "name": "DB_PASSWORD",
    "valueFrom": "arn:aws:secretsmanager:eu-west-2:111122223333:secret:agent/db-XyZ123:password::" },
  { "name": "DB_HOST",
    "valueFrom": "arn:aws:ssm:eu-west-2:111122223333:parameter/agent/db-host" } ]
A whole secret: the full value of agent/search becomes $SEARCH_API_KEY. With no version given, ECS fetches the version labelled AWSCURRENT.[7]
One JSON key: the database secret is JSON ({"username": …, "password": …}). The ARN ends :json-key:version-stage:version-id, so :password:: means "the password key, default version". The trailing colons are required even when empty. Needs Fargate platform 1.4.0 or later.[7]
A Parameter Store value: SSM Parameter Store also works in secrets. Here it holds a hostname, which isn't really secret, but keeps all database settings in one place. The execution role needs ssm:GetParameters for this one, secretsmanager:GetSecretValue for the others, and kms:Decrypt if a secret uses your own KMS key.[8]

Three things that bite

FactConsequence
Fetched once, at container startRotate the database password and running tasks keep the old one. They'll get auth errors until replaced. Fix: Force new deployment, which rolls the tasks the safe way from lesson 6.[7] For secrets that rotate often, have the app read them at runtime with the SDK, using the task role.
Fetched before your code runsA wrong ARN or a missing permission stops the task with ResourceInitializationError: unable to pull secrets or registry auth….[9] Your code never started, so look at the execution role (and the network path to Secrets Manager, lesson 3), not at your logs.
It becomes an environment variableYour app, its logs and debugging tools can all see it.[7] Never log os.environ, and never bake a key into the image: anyone who can pull it can read it.

What is a CVE?

CVE stands for Common Vulnerabilities and Exposures. It's a public catalogue of known security flaws in software, run by the non-profit MITRE with US government funding. Each flaw gets one ID, so everyone (vendors, scanners, you) can talk about the same bug.[10]

CVE-2024-3094
    │    └── a sequence number
    └────── the year the ID was assigned

That one was a backdoor hidden in xz-utils, a compression library that ships with many Linux base images. A CVE ID names the flaw. It doesn't say how bad it is: that's a separate severity (CRITICAL, HIGH, MEDIUM, LOW), usually based on a 0 to 10 CVSS score.

How it connects to ECR scanning: a scanner lists every package in your image and its version, then checks that list against the CVE database. Each match is a finding: the CVE ID, its severity, the affected package and version, and often the version that fixes it.[6] The usual fix is to rebuild the image with the patched version and deploy the new tag.

  • A CVE in xz-utils is in an OS package: basic scanning finds it.
  • A CVE in scipy is in a language package: only enhanced scanning finds it.
  • New CVEs are published all the time, so an image that scanned clean last month can have findings today. That's why enhanced scanning offers continuous rescans.
Which one pins the image: a service or a standalone task?

Only a service. A standalone task resolves the tag fresh every time it starts.[1]

Memory hook: pinning needs something that remembers. A service has a deployment that lasts between tasks, and that's where ECS stores the digest. A standalone task has nothing that lasts between runs: each RunTask starts from zero, reads the tag, and gets whatever it points at today.

Service (forecast API)Standalone task (retraining job)
Tag resolvedOnce per deploymentAt every start
Tag moves, then...Nothing changes until a new deploymentThe next run uses the new image
Risk with a movable tagPinned image deleted by cleanupSame revision, different code

Immutable, unique tags remove both risks.
