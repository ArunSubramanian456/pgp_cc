Scaling a service

More tasks when work piles up, fewer when it doesn't, and no solve lost along the way

Your win for this lesson (about 25 minutes) You can choose the right scaling metric for a web API and for a queue worker, work out roughly how many tasks ECS will run, and explain how a worker avoids losing a half-finished MILP solve when the service scales in.

Warm-up

From lessons 2 to 6. Answer from memory before you click. Read each question carefully: one word can change the answer.

1 · What scaling actually changes

Every service has a desiredCount. Service Auto Scaling does one thing: it moves that number up and down between a minimum and a maximum that you set. The service then does what it always does (lesson 1): it starts or stops tasks until the running count matches.[1]

a metric (CPU, requests, queue backlog)
   → crosses the target            (alarms that auto scaling creates and manages for you)
   → desiredCount changes          (never below min, never above max)
   → the service starts or stops tasks

Behind the scenes, ECS uses a separate service called Application Auto Scaling. Treat it as a black box: you give it a range and a policy, and it sets desiredCount.[1] There are three kinds of policy:

PolicyYou sayUse it for
Target tracking"Keep this metric near this value"The default choice. Most services, including queue workers[4]
Step scaling"When the alarm is this far past the line, add this many"When you want full control over step sizes and how fast it reacts
Scheduled"At 07:00 on Mondays, set min to 6"Known peaks, like planners opening the weekly forecast on Monday morning[3]

This lesson focuses on target tracking.

2 · The forecast API: target tracking on CPU

The forecast API from lesson 6 runs model inference on CPU. When requests rise, CPU rises, so average CPU is a good signal. Say what each highlighted part does, then click to check.

aws application-autoscaling register-scalable-target \
  --service-namespace ecs --scalable-dimension ecs:service:DesiredCount \
  --resource-id service/forecasting/forecast-api \
  --min-capacity 2 --max-capacity 10

{
  "PredefinedMetricSpecification": { "PredefinedMetricType": "ECSServiceAverageCPUUtilization" },
  "TargetValue": 60.0,
  "ScaleOutCooldown": 60,
  "ScaleInCooldown": 300
}
The scalable target: the range auto scaling may move desiredCount in, here 2 to 10.[5] The minimum of 2 is the forecast API's availability floor: one task can fail or be replaced while the other keeps serving. The maximum is your cost ceiling, and it also has to fit your Fargate vCPU quota (lesson 5).
The metric: average CPU across the service's tasks. The other two built-in choices are ECSServiceAverageMemoryUtilization and ALBRequestCountPerTarget (requests per task per minute, from the load balancer).[6] Pick the one that actually rises when the app gets busy.
TargetValue: keep average CPU near 60%. Why not 90%? New tasks need about 90 seconds to pull the image and load the model before they help. The gap between 60% and 100% is the room the running tasks have to absorb a spike in the meantime.
Cooldowns (seconds): how long to wait after scaling before scaling again in the same direction, so new tasks have time to start and show up in the metric. Short for scaling out, long for scaling in: adding tasks fast protects users, and removing them slowly avoids flapping up and down.

How many tasks? Roughly proportional

Target tracking scales in proportion to the metric.[2] A useful rule of thumb:

new desiredCount ≈ current tasks × (current metric ÷ target)

It's approximate, because ECS rounds cautiously: up when adding, so it never adds too little, and carefully when removing.[2]

Five behaviours worth knowing

  • Out fast, in slowly. It scales out as fast as it can and scales in gradually.[2]
  • No data, no action. If the metric has no data, nothing happens. Missing data is not treated as "low", so it never scales in because of it.[2]
  • Several policies: out if any, in only if all. You can have, say, a CPU policy and a requests policy. It scales out if any of them wants to, and scales in only when all of them agree.[2]
  • Deployments pause scale-in. While a deployment (lesson 6) is in progress, scale-in is turned off. Scale-out keeps working.[1]
  • Hands off its alarms. Don't edit or delete the CloudWatch alarms a target tracking policy creates. Deleting the policy removes them.[2]
CPU isn't always the right signal The agentic data-exploration assistant spends most of each request waiting for an LLM to reply. Its CPU sits near 5% even when users are queuing up, so a CPU policy would never scale it out. Requests per task (ALBRequestCountPerTarget) does rise with load, so that's the one to track. Always ask: "which number actually goes up when this app is busy?"

3 · The solve-on-demand worker: scaling on a queue

New app. Supply chain planners click "re-optimise" in a dashboard, and each click puts a MILP solve job on an SQS queue. A worker service (no load balancer) pulls jobs, solves them and writes the result to S3. A solve takes about 30 seconds. Planners are happy to wait up to 10 minutes.

Why not scale on queue depth directly? The number of messages waiting tells you there's work, but it doesn't change in proportion to the number of tasks working on it. A target tracking policy on raw depth reads a big queue as a demand for proportionally more tasks, and can scale far beyond what you need.[4] CPU doesn't help either: a busy worker sits near 100% CPU whether 5 or 5,000 jobs are waiting.

Track the backlog per task instead.[4]

backlog per task = messages visible in the queue ÷ running tasks
target value     = acceptable wait ÷ time to process one message

For the solve worker: 600 s acceptable wait ÷ 30 s per solve = a target of 20 jobs per task. A task with 20 jobs ahead of it finishes the last one in about 10 minutes. AWS's own example is the same arithmetic: 10 s ÷ 0.1 s = 100 messages per task.[7]

You don't write code to calculate it. The policy divides one metric by the other itself (CloudWatch "metric math"), using two numbers:[4]

  • ApproximateNumberOfMessagesVisible from SQS: the jobs waiting.
  • RunningTaskCount from ECS: the tasks running. This one only exists if Container Insights is turned on for the cluster. Without it, the division has no data, and (as in section 2) no data means no scaling at all.[4]

Keep the worker's minimum at 1 or more for this policy: with zero tasks, "jobs ÷ running tasks" has nothing to divide by. Scaling a worker to zero when the queue is empty is possible, but needs a different setup (ask me if you want it).

4 · Scaling in without losing a solve

When the queue drains, auto scaling lowers desiredCount, and ECS stops some workers. You know the stop sequence from lessons 2 and 4: SIGTERM, then SIGKILL after stopTimeout (at most 120 seconds on Fargate). Now suppose that worker is 20 seconds into a 30-second solve. What happens to the job?

The worker never deleted the message, so it isn't lost. Once its visibility timeout runs out, SQS makes it visible again and another worker picks it up.[4] That's safe, but wasteful, and it only works if you get three things right:

Get this rightWhy
Visibility timeout ≥ your longest solveThe default is 30 seconds.[8] If a solve takes 4 minutes, the message reappears after 30 s while the first worker is still solving, and a second worker starts the same job.
Idempotent resultsA message can be handled twice, so write the result under a key that depends only on the job, e.g. results/{job_id}.json. A second run overwrites it with the same answer. Same idea as the Scenario Lab keys in lesson 5.
Task scale-in protectionStops ECS from choosing a busy worker when it scales in. See below.

Task scale-in protection

This is an ECS feature. A worker can mark its own task as protected while it works on a job. A protected task isn't stopped by auto scaling scale-in or by deployments.[9] ECS gives every container an environment variable, ECS_AGENT_URI, and the worker calls an endpoint under it. The worker loop:

while not shutting_down:
    msg = queue.receive()                       # invisible to other workers now
    PUT $ECS_AGENT_URI/task-protection/v1/state  {"ProtectionEnabled": true, "ExpiresInMinutes": 15}
    result = solve_milp(msg.body)
    s3.put(f"results/{msg.job_id}.json", result)
    queue.delete(msg)
    PUT $ECS_AGENT_URI/task-protection/v1/state  {"ProtectionEnabled": false}
Receive: SQS hides the message from other workers for the visibility timeout. Set that longer than the slowest solve.
Protect: from now on, scale-in and deployments leave this task alone. ExpiresInMinutes can be 1 to 2,880 (48 hours). If you leave it out, protection lasts 120 minutes, then switches itself off.[9] That expiry is your safety net: a worker stuck on a solve that never finishes can't block scale-in forever. Pick a value a bit above your slowest solve.
Write the result under a key that depends only on the job, so a repeat run is harmless.
Unprotect: the task can be stopped again, so the next scale-in can choose it while it's idle between messages. Recommended by AWS for queue workers: the task protects itself through this endpoint.[10]

Two limits to remember:

  • Services only. It works only for tasks that belong to a service. For a standalone task (like the nightly planner from lesson 4), the call fails with TASK_NOT_VALID. A standalone task has no scale-in to be protected from anyway.[11]
  • Scale-in and deployments only. It doesn't stop a Fargate Spot interruption or a crash. That's why the visibility timeout and idempotent results still matter.

Also handle SIGTERM: when the worker gets it, stop taking new messages and finish (or abandon) the current one within stopTimeout. An abandoned message simply reappears after its visibility timeout.

Practice

Your questions from this session

Try to answer each one out loud before opening it.

What does register-scalable-target do? Is it only for auto scaling, and does it work for EC2, ECS, EKS?

It belongs to Application Auto Scaling, a separate AWS service (CLI: aws application-autoscaling), not to ECS. It tells that service: "this number on this resource may be scaled, within this range." On its own it scales nothing. Nothing moves until you also attach a policy (put-scaling-policy) or a scheduled action.[5]

--service-namespace ecs                      which AWS service owns the resource
--scalable-dimension ecs:service:DesiredCount which number on it to change
--resource-id service/forecasting/forecast-api service/<cluster>/<service>
--min-capacity 2 --max-capacity 10            the range policies may move it in

Running it again on the same target updates the range. The same command can also pause scaling, which is how you'd stop scale-out during a deployment (section 2).[1]

ResourceScaled by
ECS services (Fargate or EC2)This command, namespace ecs
SageMaker endpoints, Lambda provisioned concurrency, DynamoDB, Aurora replicas, ElastiCache, Spot Fleet and moreThis same command, with a different namespace and dimension[12]
EC2 Auto Scaling groupsNot this. A different service with its own CLI, aws autoscaling. Same ideas (min, max, desired, target tracking).
EKSNot this. Kubernetes scales its own pods and nodes (out of scope for this course).

Follow-up: is it a separate service in the console too? It's a real AWS service (its own API, CLI, SDK, IAM actions application-autoscaling:* and CloudFormation types AWS::ApplicationAutoScaling::ScalableTarget and ::ScalingPolicy), but it has no console page of its own. In the console, you set it up inside the service you're scaling: for ECS, in the service's Service auto scaling settings. The console then makes the Application Auto Scaling calls for you.[13] The alarms that target tracking creates show up in the CloudWatch console.

Follow-up: so where does it fit among task definition, cluster, service and task? It attaches to the service only, and comes after the service exists:

task definition   the recipe: knows nothing about how many copies     no scaling here
cluster           a grouping: holds services and tasks                 no scaling here
standalone task   no desiredCount, nothing to keep at a number         no scaling here
service           has desiredCount                                     ← scaling attaches here
  then: register-scalable-target service/<cluster>/<service>  +  put-scaling-policy

The console shows it as an optional section when you create or update a service, which makes it look like a service setting. The ECS API's CreateService has no scaling fields, though. It's always a separate step that points at the service. Once it's on, auto scaling sets desiredCount: if you change the count by hand, its next decision can change it back.

On Fargate, scaling the service is all you do: there are no servers to scale. With ECS on EC2 you'd also need the instances to grow, which is lesson 10's topic.

Is a "worker service" a separate option in ECS?

No. It's an ordinary ECS service: same task definition format, same CreateService call. "Worker" describes what the code does (pull jobs from a queue), not an ECS setting. What makes it a worker is what you leave out and what you add:

Web service (forecast API)Worker service (solve worker)
Port mappingsYes (8000)None: nothing connects to it
loadBalancersTarget groupNone
Health checkALB target group checkContainer healthCheck only
Security group inboundFrom the ALBNone
Scales onCPU or requests per taskBacklog per task
CodeAnswers HTTP requestsLoops: receive → protect → work → write → delete → unprotect
// task definition (excerpt)
"containerDefinitions": [{
  "name": "worker", "image": "…/solve-worker:2026-10-25-a1b2c3d", "essential": true,
  "environment": [{ "name": "QUEUE_URL", "value": "https://sqs.eu-west-2.amazonaws.com/…/solve-jobs" }],
  "healthCheck": { "command": ["CMD-SHELL", "find /tmp/heartbeat -mmin -5 | grep -q . || exit 1"],
                   "startPeriod": 60 },
  "stopTimeout": 120
}]
// no portMappings: nothing ever connects in

// service: the same create-service as any other, just without a load balancer
aws ecs create-service --cluster planning --service-name solve-worker \
  --task-definition solve-worker:4 --desired-count 2 \
  --capacity-provider-strategy capacityProvider=FARGATE,base=1,weight=1 capacityProvider=FARGATE_SPOT,weight=3 \
  --network-configuration "awsvpcConfiguration={subnets=[private-a,private-b],securityGroups=[sg-worker],assignPublicIp=DISABLED}"

Follow-up: where does SQS live? Outside ECS and outside your VPC. SQS is its own fully managed AWS service; you create the queue separately (console, CLI or the same CDK stack). ECS doesn't know the queue exists. Your code talks to it through the SDK:

API task  ──SendMessage──▶  [ SQS queue: solve-jobs ]  ◀──ReceiveMessage / DeleteMessage──  worker tasks
(task role: sqs:SendMessage)      AWS-managed,              (task role: sqs:ReceiveMessage, sqs:DeleteMessage)
                                  outside your VPC
          Application Auto Scaling reads the queue's CloudWatch metric → sets the worker service's desiredCount
  • Both gates apply (lesson 11): a network route to SQS from private subnets (NAT or an sqs interface endpoint) and the task role permissions.
  • The queue URL reaches the code as a plain environment value.
  • Queue settings belong to SQS, not ECS: visibility timeout (above the longest job), retention, and a dead-letter queue for messages that keep failing.
  • The only ECS-side link is scaling, which reads the queue's metric.

Follow-up: who puts jobs on the queue? Any code that calls SendMessage: the producer. For Scenario Lab, where planners request runs in a browser:

browser ─▶ ALB ─▶ frontend service (UI) ─Service Connect─▶ scenario-api service
                                                             1. validate the request, create run_id
                                                             2. write inputs to S3: runs/{run_id}/scenario-{n}.json
                                                             3. SendMessage × N  {run_id, scenario_id}
                                                             4. reply at once: {"run_id": "r-17"}
                                        [ SQS: scenario-jobs ] ─▶ worker service (mostly Spot)
                                                                    solve → results/{run_id}/{scenario_id}.json
   browser polls GET /runs/r-17 ─▶ scenario-api counts results; when all N are in,
                                   RunTask compare (standalone) → baseline vs scenarios report
  • Recommended producer: an API service, not the UI. One place validates input, assigns IDs and holds the sqs:SendMessage permission; the UI's task role needs nothing. It's the same pattern as the capstone.
  • Simpler start: a small team can let a Streamlit frontend send to SQS directly (one service instead of two), then split out the API when it grows. A deliberate trade-off.
  • Other producers: a scheduled task (nightly batches), or AWS events such as a file landing in S3. The worker doesn't care who sent the message.

Follow-up: where does the compare task get the results? From S3. Tasks never talk to each other directly; S3 is the hand-off point:

scenario-api  writes runs/{run_id}/manifest.json   ← list of expected scenario_ids + baseline id
workers       write  results/{run_id}/{scenario_id}.json
scenario-api  RunTask compare  with override RUN_ID=r-17
compare task  1. read the manifest                       (what should exist)
              2. read every results/{run_id}/*.json      (what does exist)
              3. reconcile: list missing or failed scenarios (lesson 5)
              4. compare each scenario with the baseline
              5. write reports/{run_id}/report.json (+ charts), exit 0
scenario-api  next poll finds the report → returns it to the browser

Its task role reads runs/* and results/* and writes reports/*. Nothing else.

Follow-up: if planners don't wait on the request, where does the answer go? Nowhere is "sent back" to the original request: the results stay in S3, and the planner fetches them. How they find out depends on how long a run takes:

Run takesHow the planner gets the result
Seconds to a few minutesThe page polls GET /runs/{run_id} every few seconds and shows progress ("31 / 48 solved"), then the report
Tens of minutes or moreThey close the page. When the compare task finishes, a notification (SNS email, or a Teams/Slack message) links to the report
AlwaysA "My runs" page lists past runs and their status, so a closed tab never loses a result

Status lives outside the tasks: counted from S3 (results vs manifest), or kept in a small runs table that workers update.

The worker writes /tmp/heartbeat after each message, so the health check fails if the loop hangs for 5 minutes. Spot fits because messages that are interrupted mid-job reappear and results are idempotent. The task role gets sqs:ReceiveMessage and sqs:DeleteMessage on that one queue.
