ECS on Fargate: building blocks

One-page cheat sheet. Print it or keep it open.

Task definition: blueprint

JSON describing one or more containers: image, CPU/memory, ports, env, logs, IAM role, volumes. It's versioned, and every edit creates a new revision (name:N). docs

Task: running copy

One instance of a task definition. Its containers start and stop together and share localhost. Run it standalone for one-off jobs that exit. docs

Service: keeps N alive

Keeps a desired count of tasks running and replaces any that stop. This is where the load balancer, deployments and autoscaling attach. Use it for long-running apps like APIs. docs

Cluster: grouping

A logical grouping of services and standalone tasks. On Fargate it's just a namespace and boundary (e.g. staging, prod), with no servers to manage.

One task = one business purpose (+ sidecars)

  • Multiple containers in one task are for sidecars: small helpers like log routers, observability agents or proxies that enhance one app container. docs
  • Frontend, API and worker each get their own task definition and service, so each scales and deploys on its own.
  • Multiple tasks = identical copies, for load and resilience.
  • Databases usually live outside ECS (e.g. RDS). Fargate task storage is temporary.
  • Test: put two containers in the same task only if they always run 1:1 and it's fine for them to restart together.

Fargate facts

  • No servers to provision, scale, pick types for, or bin-pack. docs
  • Each task gets its own isolation boundary, with no shared kernel, CPU, memory or network interface. Tasks and compute are 1:1. docs
  • Network mode is always awsvpc, so every task has its own ENI. You choose its subnets and security groups. docs
  • CPU and memory are set at task level, from valid pairs. The smallest is 256 CPU units (.25 vCPU) with 512 MiB. docs
  • Set requiresCompatibilities: ["FARGATE"] in the task definition.
  • Fargate Spot is cheaper but can be interrupted with a 2-minute warning. Use it for batch jobs and dev/staging. docs
