Running many jobs on Fargate

Choosing a shape, concurrency from quota, Step Functions Map, Spot and idempotency.

Pick the shape

ShapeUse when
RunTask loopA handful of jobs. You'd own retries, limits and tracking yourself
Step Functions Map + ecs:runTask.syncA batch with a known end, followed by a step that needs all the results
SQS + worker serviceA continuous stream of requests; scale on backlog (lesson 6)

count (≤ 10) starts identical copies with the same overrides, so it's no use for different scenarios.

Limits to plan around

  • Fargate vCPU quota: concurrent vCPUs per account and Region, with separate On-Demand and Spot quotas. The new-account On-Demand default is 6. Check it in Service Quotas before the first run. docs
  • Launch rate: Fargate RunTask is limited to 20 calls per second. docs
  • Max at once = (quota − other usage) ÷ vCPU per task.
  • Inline Map: a hard ceiling of 40 concurrent (MaxConcurrency can only go lower), ≤ 25,000 history events, input ≤ 256 KiB. Beyond any of these, use Distributed (≤ 10,000 child executions). docs
  • Payloads: Step Functions state input and output ≤ 256 KiB. Shrink each iteration's Output to {id, status}.
  • Overrides ≤ 8,192 characters, so pass IDs and keep the real inputs in S3.

Map iteration checklist

  • .sync so the iteration waits for the task to stop
  • Pinned TaskDefinition revision for the whole run
  • MaxConcurrency set from your quota
  • Retry ECS.AmazonECSException / AmazonECS.Unknown (launch) with backoff
  • Retry States.TaskFailed a couple of times (e.g. Spot). Test how exit codes map to errors
  • Catch States.ALL per iteration, so one failure can't fail the whole Map

Parameters are PascalCase. A non-empty failures list fails the state with AmazonECS.Unknown. docs

Fargate Spot

  • Two-minute warning: a task state change event plus SIGTERM
  • stopCode: TerminationNotice, "Your Spot Task was interrupted."
  • stopTimeout ≤ 120 s to use the warning
  • No automatic fallback to on-demand. Add a Catch path for that if you need it

docs

Idempotent jobs

  • Output key = f(run_id, scenario_id), so a retry overwrites rather than duplicates.
  • Write the result last, in one PUT. Exit 0 only after it succeeds.
  • Long solves: checkpoint the incumbent to S3 and warm-start the retry.
  • The final step reconciles results against a manifest and marks gaps as MISSING.
