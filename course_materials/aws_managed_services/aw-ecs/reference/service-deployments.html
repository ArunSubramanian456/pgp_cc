Deploying an ECS service

Rolling updates, health, rollback, traffic-shifting strategies.

Start a deployment

aws ecs update-service --cluster C --service S --task-definition family:NEW_REVISION
aws ecs update-service --cluster C --service S --force-new-deployment     # same revision, fresh tasks (e.g. rotated secret)

Two separate steps: register-task-definition saves the revision (image tag not checked) → update-service starts the deployment. A wrong tag only fails when an :N task launches and pulls: CannotPullContainerError, task never reaches RUNNING.

Rollout state: IN_PROGRESS → COMPLETED (steady state) or FAILED.

Circuit breaker (rolling only)

  • {"enable": true, "rollback": true}
  • Stage 1: do tasks reach RUNNING? Stage 2: do they pass health checks?
  • Default threshold: 0.5 × desired, min 3, max 200 failed tasks
  • Rolls back to the last COMPLETED deployment (if none exists, the deployment just stops)
  • Alert on the SERVICE_DEPLOYMENT_FAILED event → SNS

docs

Alarm-based rollback

  • "alarms": {"alarmNames": [...], "enable": true, "rollback": true}
  • Catches healthy but wrong: error rate, latency
  • The only failure detection for blue/green, linear and canary

Healthy ≠ correct. The circuit breaker only sees starting and health checks.

Strategies (deploymentConfiguration.strategy)

StrategyTrafficUse when
ROLLINGTasks replaced in batchesThe default; cheap; circuit breaker available
BLUE_GREENEverything shifts in one stepYou want an instant switch and an instant rollback
LINEAREqual steps with a pause between themGradual, watched rollout
CANARYA small % first, a pause, then the restA risky change, e.g. a new model architecture

Bake time keeps the old version running after the shift, so rollback is instant. You pay for both versions meanwhile. blog
