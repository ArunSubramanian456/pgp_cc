ECS design review checklist

Eight questions to ask of any app before it goes on ECS.

1 · Shape

  • Always on → service. Runs and exits → standalone/scheduled task. Queue of work → worker service.
  • One business purpose per task definition; sidecars only for true 1:1 helpers.
  • Different trust level → different task definition (own roles, own network).

2 · Networking

  • Public ALB, private tasks, no public IPs.
  • Security groups chained by group ID, not CIDR.
  • Every outbound call has a route: NAT (internet) or VPC endpoints (AWS services).
  • Timeouts line up (ALB idle 60 s default vs slowest request).

3 · Roles and secrets

  • Execution role: pull, logs, secrets. Task role: what the code calls, least privilege.
  • AWS APIs via task role, never keys. Other keys in Secrets Manager via secrets.
  • Rotation plan: new deployment or read at runtime.

4 · Deployments

  • Rolling 100/200 (or canary/linear/blue-green with reason).
  • Grace period ≥ startup; deregistration delay ≥ longest request; SIGTERM handled.
  • Circuit breaker with rollback + alarm for "healthy but wrong".

5 · Scaling and quotas

  • Metric that rises with load (CPU, requests per target, backlog per task).
  • Min for availability, max for cost; scheduled scaling for known peaks.
  • Max × task vCPU (plus jobs) fits the Fargate vCPU quota.

6 · Images

  • Repo per image; immutable unique tags; never deploy latest.
  • Lifecycle rules can't reach deployed images.
  • Scanning matches the risk (enhanced for language packages).
  • Built for the task's CPU architecture.

7 · Observability

  • awslogs with retention; a request/job ID in every log line; no secrets in logs.
  • Container Insights; event capture for stopped-task history.
  • ECS Exec only where justified.

8 · Compute and cost

  • Fargate unless GPU / >32 vCPU / privileged → Managed Instances.
  • Spot only for interruptible, retry-safe work; ARM64 if libraries allow.
  • Estimate tasks × hours × (vCPU + GB) and add ALB, NAT, endpoints, logs.

Role, security group, or both?

  • Network (route + SGs on both ends): every connection. Fails as a timeout.
  • IAM: only calls to AWS service APIs. Fails as AccessDenied.
  • AWS API call → both. ECS doing it (pull, logs, secrets) → execution role; your code → task role.
  • Not AWS (Postgres, third-party APIs, service-to-service HTTP) → network + the app's own login.
