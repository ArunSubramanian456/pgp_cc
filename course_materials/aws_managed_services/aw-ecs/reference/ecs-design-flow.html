ECS design flow

Designing an app on ECS (Fargate), step by step. Each step ends with what you should have decided; the details live in the linked sheets.

0 inputs → 1 shape → 2 task definitions → 3 network + service/task settings → 4 deployments
         → 5 scaling → 6 observability → 7 compute + cost → 8 security + failure review → 9 write it as code

Steps marked added weren't in your original list. Work in order, but expect to loop back: step 7's cost often changes a step 3 choice, such as how many NAT gateways.

0 · Gather the inputs added

Every later decision depends on these. Write them down first:

  • Who waits for what? A user waiting for a reply (seconds), or nobody (background work)?
  • How long does each unit of work take? Milliseconds, minutes, hours?
  • Traffic shape: steady, business hours, known peaks, bursts.
  • Trust: does anything run code you didn't write (LLM output, user uploads)?
  • Data: how sensitive is it, and where does it live (S3, RDS, ElastiCache)?
  • Special hardware: GPU, >32 vCPU or >244 GB, privileged containers?
  • Team and budget: who runs it at 3 a.m., and what can it cost per month?
Done when: you can answer all seven in a sentence each.

1 · Shape: services, tasks, and how many task definitions

If the piece…It's a…
is always on and answers requestsService (behind an ALB if users call it; reached by Service Connect if only other services call it)
works through a queue of jobsWorker service fed by SQS: a normal service with no ports or load balancer (not a separate ECS type)
runs, finishes and exitsStandalone task (RunTask) or a scheduled task (EventBridge Scheduler)
runs many independent jobs at onceMany standalone tasks, or a worker service
runs untrusted codeIts own task definition, one task per run, never a sidecar
is a helper bound 1:1 to one app (log router, telemetry, proxy)Sidecar container in that app's task definition
  • One business purpose = one task definition. Split further when trust, lifetime or scaling differ.
  • Calls to Bedrock, a database or another API are code, not separate pieces.
  • Decide how pieces talk: synchronous HTTP (someone is waiting) or a queue (nobody is). Long work → the async pattern: start, return an ID, poll.
  • State lives outside tasks (S3, RDS, ElastiCache), because tasks are replaced at any time.
Done when: you have a list like "frontend = service, api = service, sandbox = standalone task per run", plus an arrow for every call between pieces, labelled HTTP, queue or RunTask.

3 · Network, and the service / task settings

Subnets (at least 2 AZs, each tier in each AZ):

TierHoldsRoute out
PublicInternet-facing ALB, NAT gateway. Nothing else.Internet gateway
Private with egressServices that call non-AWS internet APIsNAT gateway
Private, isolatedUntrusted-code tasks, databases, anything that must never reach the internetNone (VPC endpoints only)

Do I need NAT? Only if something calls a non-AWS internet address (third-party APIs, public package mirrors at runtime). AWS services can be reached through endpoints instead.

VPC endpoints: always the free S3 gateway endpoint. For any task with no NAT route: ecr.api, ecr.dkr, logs (it can't start without them), plus secretsmanager / ssm if it has secrets. Then per service called: bedrock-runtime, sqs, ecs (for RunTask), ssmmessages (ECS Exec). Each interface endpoint costs per hour per AZ.

Security groups: one per piece. Inbound rules name the caller's group, not IP ranges. Outbound: open only where needed; locked down (allow-all off) for untrusted code. Write the chain: internet → ALB → app → API → DB.

How pieces connect: internet → public ALB (HTTPS listener, ACM certificate, target group type ip, health check path, idle timeout, stickiness if sessions live in memory). Service → service: Service Connect. Service → its own tasks: RunTask. Anything slower than the ALB idle timeout (60 s): use the async pattern.

4 · Deployments

  • Strategy: rolling (default, min 100% / max 200%), or blue/green, linear, canary when you need traffic shifting and a bake time.
  • Three timers: grace period / startPeriod (startup) · deregistration delay just above your longest request (draining) · stopTimeout with SIGTERM handling (shutdown).
  • Two safety nets: circuit breaker with rollback (tasks that won't start or stay healthy) + CloudWatch alarm rollback (healthy but wrong: 5xx, error rate).
  • Release order: things that are called before their callers; new task definition revision before the service that names it; keep changes backward compatible.
  • Pinning: services pin the image digest per deployment; standalone tasks resolve the tag every run, so name exact revisions and immutable tags.
  • Secrets rotation: force a new deployment, or read the secret at runtime.
  • Sessions in memory (e.g. Streamlit) are cut when a task is replaced: keep state outside the task, release off-hours.
Done when: you can say what happens, second by second, when a bad release goes out, and why users don't notice.

  • Quotas: sum of (max tasks × vCPU) across everything must fit the Fargate vCPU quota; RunTask has a rate limit.

6 · Observability and debugging

  • Logs: awslogs per container, a retention period, a request / job / run ID in every line, step timings, never secrets.
  • Metrics: Container Insights (enhanced) on the cluster.
  • History: event capture, so stopped tasks are visible for longer than an hour.
  • Alarms: 5xx rate, latency, queue age, failed runs, used for rollback and paging.
  • Access: ECS Exec only where justified (task role ssmmessages, endpoint if no NAT); off for untrusted code.
  • Playbook: did my code run? No → stoppedReason; yes → exit code + logs; alive but wrong → metrics + Exec. Timeout = network gate; AccessDenied = IAM gate.
Done when: for "it won't start", "it's slow" and "it's wrong", you know the first place to look.

7 · Compute and cost

  • Compute: Fargate by default (per-task isolation) · Managed Instances for GPUs, >32 vCPU / 244 GB, privileged · EC2 launch type only for full host control · Spot only for interruptible, retry-safe work · Express Mode as a shortcut for a public web service.
  • Fargate maths: tasks × hours × (vCPU × vCPU price + GB × GB price); always-on = 720 h; ARM ≈ 20% less.
  • Fixed costs: ALB, NAT (per hour + per GB), interface endpoints (per hour per AZ), public IPv4, logs, Container Insights. For small apps these can match the compute.
  • Levers: ARM64, Spot, scheduled scale-down out of hours, fewer endpoints vs NAT data charges, Savings Plans once steady.
Done when: you have a monthly estimate, compute and fixed network separately, and know your biggest line (often not ECS: model tokens, the database).

8 · Security and failure review added

Security pass: no public IPs on tasks · every role least-privilege (and PassRole scoped, never *) · secrets never in environment or images · untrusted code isolated (own task, isolated subnets, no outbound, tiny role) · images scanned · DB users read-only where possible.

Failure pass: for each, say what happens and how you'd notice:

  • a task crashes · an AZ fails (and with it, a single NAT) · a Spot task is reclaimed
  • a dependency is slow or down (Bedrock, the DB, a third-party API) · a bad release ships
  • a secret rotates · a cleanup rule deletes an image · the vCPU quota is reached
Done when: every failure has a behaviour you chose and an alarm or log line that tells you it happened.
